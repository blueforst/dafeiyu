# 按链接补录公开消息

补录用于找回未被正常来源采集到的公开消息。管理员只提交帖子链接；服务先保存检查请求，不在提交接口中打开浏览器、调用模型或发送消息。

链接必须使用 HTTPS，指向 `x.com` 或 `twitter.com` 的明确 `<handle>/status/<平台ID>` 路径。`mobile.`、`www.` 前缀、末尾斜线及分享查询参数会规整为 `https://x.com/<handle>/status/<平台ID>`。含账号密码、非默认端口、其他站点、图片子路径或聊天地址的输入会被拒绝。

每个工作账号最多保留二十条待处理请求。同一平台 ID 已有待处理请求时复用原请求；已有消息时立即显示 `duplicate` 与原消息状态，不重新入队，也不唤醒浏览器检查。原消息仍可按原有规则操作，`unknown` 及已有冻结出站不会因补录而重置。

主程序恢复后的轮次，在公开采集前使用同一浏览器串行入口检查，每轮最多三条，并共享公开采集的截止时间。暂停、人工接管、排空、信号中止、预算耗尽或账号切换时，未完成的请求继续保留为 `pending`。

检查必须取得与链接一致的唯一公开目标，并确认作者不是当前工作账号，正文提及当前账号或可靠上文包含其帖子，平台时间可靠且仍在处理时效内。通过后经正常分级入口入库，并在同一事务中写入“管理员补录”优先标记。遗忘、来源保护与消息去重仍有效；额度、退避、草稿模式和发送前校验仍走原工作流。补录本身不会直接生成或发送回复。

请求状态为：

- `pending`：等待轮次检查。
- `imported`：已优先入队，后续状态以关联消息为准。
- `duplicate`：已有消息，显示其当前状态。
- `rejected`：自己的帖子、无关、超时或受遗忘／来源保护等不允许入队的消息。
- `failed`：页面读取或可靠结构检查失败，可重新提交链接。

接口沿用应用的管理鉴权和控制请求标记：

| 接口 | 行为 |
| --- | --- |
| `POST /api/messages/import` | 提交 `{url}`；返回补录请求及 `pending`／`duplicate` 结果 |
| `GET /api/messages/imports` | 分页读取当前账号结果；可按 `status` 筛选 |
| `GET /api/messages/imports/:id` | 读取当前账号单项结果 |

列表返回 `items`、`nextCursor` 和当前账号的 `pending` 数量。请求包含 `messageId`、`messageStatus`、固定原因及时间；`revision` 对应只读更新时间。消息详情可通过 `manualImports` 关联补录结果。常规 `manual-import` 日志仅记录内部请求 ID、账号和结果，不记录帖子正文、URL 或底层异常。

服务的隔离回归包含真实 SQLite、Fastify 入口、分级事务与草稿工作流，浏览器检查使用注入夹具；真实平台补录、回复及双方回执另行验收。本轮后端回归通过不代表真实 X 收发已经通过。
