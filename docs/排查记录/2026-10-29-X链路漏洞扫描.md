## X01 · P1：等待身份检查的旧启动请求覆盖后来的暂停或接管

位置：[workflow.ts](../../src/workflow.ts#L64)，重点为第 72–75 行；HTTP 入口为 [app.ts](../../src/app.ts#L94)。

`resume()` 只在开始时检查 `manual`／`draining`，随后等待空闲和身份查询，最后无条件把浏览器设为 `auto`、业务设为 `running`。这些异步等待期间没有运行控制互斥或请求修订检查。

触发顺序：

1. 从暂停状态请求启动，身份检查尚未返回。
2. 另一页面或并发请求执行暂停／接管，并已成功返回。
3. 旧启动请求的身份检查返回有效账号。
4. 旧请求继续写入 `auto`／`running`，覆盖用户后发出的操作。

正式镜像复现结果：

| 分支 | 后发操作完成后的状态 | 旧启动请求返回后的状态 | 浏览器控制顺序 |
| --- | --- | --- | --- |
| `X01-pause` | `paused` | `running` | `paused → auto` |
| `X01-takeover` | `manual` | `running` | `manual → auto` |

影响：暂停已经成功返回后，自动工作仍可重新运行；人工接管可被旧启动请求撤回。后续满足额度、时段和 unknown 门禁时，业务可继续自动生成和发送。问题需要管理操作并发，不涉及匿名访问。

建议：统一串行化应用层运行控制，或为每次控制请求递增修订并在每个异步提交边界核验；新暂停／接管必须使旧启动请求失效。回归应覆盖身份慢响应、浏览器控制慢响应、多页面并发和异常返回。

## X02 · P1：页面同现或前后顺序被误当成可信回复关系

位置：[public-collection.ts](../../src/public-collection.ts#L152) 第 154–156 行；[public-target.ts](../../src/public-target.ts#L53) 第 53、84 行；[manual-imports.ts](../../src/manual-imports.ts#L83) 第 83–85 行。

存在两条可独立到达的路径：

- **自己帖子下的自动采集**：只要在页面中见过自己的目标帖子，就把同页所有非自己作者的文章加入回复队列，没有校验文章是否确实回复该目标或其已验证后代。自己的目标帖和推荐帖同时出现时，推荐帖也能作为候选。
- **上下文及按链接补录**：`waitForPublicTarget()` 把目标前面最多十一篇文章作为上文；`inspectPublicPost()` 把这些作者变成 `ancestorHandles`。补录再把其中出现工作账号当作关系通过的证据。DOM 顺序本身不证明父子关系，错误上文还被标记为 `contextIncomplete: false`。

正式镜像复现结果：

| 分支 | 合成输入 | 实际结果 |
| --- | --- | --- |
| `X02-unrelated-post` | 自己帖子 `600` 和没有提及账号、没有已验证回复关系的文章 `601` 同页 | 采集标记 `ok`；文章进入正常分级与生成；发送替身收到目标 `601` |
| `X02-manual-ancestor` | 目标 `802` 前放置另一条工作账号文章 `801`，目标无账号提及 | `ancestorHandles` 包含工作账号，`contextIncomplete=false`，补录结果为 `imported` |

影响：在运行、自动模式、开放时段且通道可发送时，可能对无关帖子生成并发布回复；错误的“上文”也会污染回复依据。暂停和既有 unknown 门禁仍然有效，本轮未声称生产页面已经出现这种推荐排列。

建议：从已验证的页面关系或页面自身已取得的原生响应建立父子链，校验采集来源与目标关联。无法证明时不把文章排入自动回复、不把作者列为祖先，并明确标记上下文不完整。不要用扩大关键词匹配或仅排除自己作者代替关系校验。回归应覆盖推荐帖、广告、前页残留、同页多个线程及真实上下文。

## X03 · P2：真实公开采集为每条回复填写不同会话 ID，使同线程合并失效

位置：[public-post.ts](../../src/public-post.ts#L51) 第 51 行；[reply-triage.ts](../../src/reply-triage.ts#L151) 第 155–160 行。

公开采集固定写入 `conversationId: match[2]`，其中 `match[2]` 是每条帖子的独立平台 ID。合并器则要求同用户的消息具有相同 `conversationId`。因此，同一个用户在自己同一篇主帖下连续发两条评论，经过现有采集后仍具有两个不同的会话 ID，无法触发三十分钟合并。

正式镜像的 `X03-thread-merge` 执行原始 `readPublicPosts()` DOM 回调，再经过公开采集和正常工作轮次：同一篇自己主帖 `700` 下的两条同作者消息，得到会话 ID `701`、`702`；模型替身调用两次，发送替身收到 `702`、`701` 两个目标，`merged` 数量为 0。

影响：已承诺的“同一会话只回复最新一条”在正常公开采集路径中失效；同线程连续留言会消耗多次生成费用和发送额度，并可能得到多条相近回复。已有合并单元测试直接提供相同会话 ID，不能证明真实采集也提供了这个条件。

建议：在确认关系后，区分独立消息平台 ID、实际回复目标 ID 和稳定线程 ID；只以可信线程 ID 合并。不要把某次浏览页面的主帖 ID 无条件赋给所有文章，否则会扩大 X02。旧消息和冻结出站保持原样，历史修复需要独立确定证据与迁移边界。

## 本轮未计为漏洞的行为

- 生产现有 `unknown` 阻塞公开通道符合当前规格。不能以解除卡顿为由重置它、改记未发送或允许重复提交。
- `not_submitted` 对应的 outbox 会进入 `cancelled`；消息虽然显示为 `draft`，再次批准返回 409。本轮确认了这条终态路径，但现有规格要求该出站停止，未把“原项不能重试”另列漏洞。界面是否应更明确展示终态可独立改善。
- 新版 Chat 缺少已验收的可靠时间及入站身份时停止自动回复，是现有明确边界，不算本轮新增故障。

## 已检查的保护和适用限制

断网复现中的十项检查：缺唯一 ID 的确认回执降为 unknown、unknown 不能再次 begin、同通道 unknown 阻塞、另一通道独立、出站按账号隔离、冻结正文不可替换、浏览器 journal 目标冻结、未提交终态重启可读、非 X 导航拒绝、缺目标不能发送，均通过。

入口静态审查同时检查了应用内部凭据、控制请求标记、Origin 检查、浏览器内部凭据、回环发布端口和示例 Nginx 配置。这不是一次对公网和所有第三方依赖的完整渗透测试，不能据此承诺不存在其他漏洞。

建议修复顺序：先 X01，随后把 X02 与 X03 按“可信关系读取 → 来源校验 → 线程合并”衔接处理。涉及关系模型的跨模块实现应按仓库要求另行编写 OpenSpec；本轮没有改动运行控制、采集、出站、历史数据或生产配置，也没有部署。
