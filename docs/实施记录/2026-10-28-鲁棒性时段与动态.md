# 回复时段与动态只读接口鲁棒性检查

## 范围与基线

本阶段以已推送的 `860ea880a81dc40e51686f3a5cdf70ba152435b0` 为代码基线，继续检查回复时段、队列有效等待时间和会话只读接口。仅编辑候选代码与确定性测试；红／绿回归由根代理在服务器独立环境执行。不访问生产数据、真实账号或模型，不改变公开每日额度的北京时间自然日口径。

## 修改前问题与调用链

### 多天排队的关闭时长被截断

现有 `replyWindow()` 只返回最近四十八小时涉及的关闭区间，而 `maxAgeHours` 允许设为 48。有效等待时间需要扣除从消息收到以来的全部关闭时长，不能用固定的四十八小时日历区间代替四十八小时有效等待。

最小例子：默认每天 23:30—08:00 关闭，从 10 月 25 日 09:00 排队到 10 月 28 日 09:00，日历时间为 72 小时，三晚共关闭 25.5 小时，实际有效等待为 **46.5 小时**，仍应符合 48 小时上限；旧实现只扣最近两晚的 17 小时，误判为 55 小时。每天只开放一分钟时，跨七天的有效等待应为七分钟，固定日历窗口的问题更明显。

调用链为 `replyWindow.closures` → `effectiveAge`／`ReplyTriage.ageSql` → 生产出队及发送判断、动态过期判定、健康与日报。修复需要保证纯函数和 SQL 使用同一口径；不能仅把固定窗口改为另一个固定天数，也不能为很短的开放窗口生成无界数量的 SQL 参数或每日查询。

### 无写入的自然过期没有更新左栏

现有会话增量按 `updated_at` 或入库时间判断变化。草稿、批准或排队消息越过有效时效时没有数据库写入；待处理总数会减少，但 `all`／`public` 等筛选下的会话增量没有返回该会话，左栏的待处理徽标和最高优先状态因而保留旧值。当前主区仅对草稿／批准补了自然过期读取，不能代替左栏更新。

拟修复路径是在会话查询中对比上次水位和当前时刻的只读资格，返回资格刚变化的会话，不写入消息时间来伪造变化。`ReplyTriage.queuedEligibility` 需要支持显式历史时刻，保持现有调用兼容；待处理判断继续复用分级口径，不另写一套时效策略。

### 历史损坏正文

新增测试检查损坏 JSON 正文是否能够降为未知或过期而不使只读接口崩溃。只有服务器红测确认后才决定是否需要修复，避免把假设写成已确认缺陷。

## 风险与恢复边界

这些修复只恢复“关闭期间暂停计算排队时效”和“会话实时显示当前待处理状态”的既定要求，不改变发送额度、出站回执、暂停或接管语义。新增配置或数据结构不是本阶段的默认选项；若确需变更，先说明调用链、复杂度、兼容方式和回退。

根代理已批准显式内部 `agePolicy`：用每日重复周期、关闭时刻、默认关闭时长与真实早安终态覆盖表达任意长历史；保留最近关闭区间用于原有展示。纯函数和 SQL 共用同一计算口径，SQL 通过 JSON 参数读取规则，不按天展开 SQL 参数。旧关闭区间数组调用仍兼容。全历史终态覆盖只用于内部计算，不进入 `/api/program` 等公开 DTO。

恢复时可回退候选源码；没有数据库迁移或数据转换。周期规则不持久化为新配置，现有发送额度、出站数据和人工控制状态保持原语义。十年跨度及一千个纯函数／SQL 样本已纳入上述时段绿测；这不表示生产长期运行或所有未测配置已经验收。

## 默认策略的性能验证入口

第一轮约 75.64 ms 中位数来自没有关闭区间的分级夹具，不能代表本阶段默认周期 SQL。`dev/feed-conversations-performance.ts` 现支持分别运行：

- `FEED_PERF_AGE_MODE=plain`：兼容旧的空区间夹具。
- `FEED_PERF_AGE_MODE=default`：真实默认 23:00 加 30 分钟至 08:00，早安任务停用，没有历史例外，使用周期 SQL。
- `FEED_PERF_AGE_MODE=history`：相同默认时刻，早安启用，临时任务表内有三十个实际提前结束的晨间终态；每次来源读取按生产方式批量只读该表，再生成带 JSON 例外的周期规则。样本数可由 `FEED_PERF_HISTORY_DAYS` 调整。

三组都使用自建临时库的一万条消息和一千个身份，保留 100 ms 建议目标，输出首次查询与后续五次耗时、真实查询计划、计时模式和参数数量。根代理统一在服务器串行验证，本机未运行；没有根据推测新增索引或迁移。

根代理先完成优化前的单 CPU 串行实测：

| 模式 | 首次查询 | 后续五次中位数 |
| --- | ---: | ---: |
| 空区间 `plain` | 92.33 ms | 83.99 ms |
| 默认周期 `default` | 133.36 ms | 116.23 ms |
| 三十条历史终态 `history` | 648.05 ms | 622.11 ms |

因此不能用空区间结果代表生产默认路径。优化前日志由根代理保留为 `before` 证据。随后只做两类有明确条件的计算跳过：

- 统计时刻尚未到首条差量，或消息时间已不早于最后差量结束时，历史例外没有重叠，不执行 `json_each`；存在交集时仍读取全部真实差量，没有截断、清空或替换历史。
- 待处理使用按状态分支的 SQL `CASE`，已确认等不参与待处理的状态不计算年龄；草稿、已批准和失败状态复用已计算的待处理资格，生成中与重写仍按原字段独立计算，避免重复。

时段第十项测试补充区间前、中、后和精确边界的纯函数／SQL 对照，并在隔离库中计数证明无交集时确实没有执行 JSON 提取；有交集的真实差量路径仍覆盖。

性能脚本保留原当前消息数据，另外提供同规模混合组：8,000 条当前消息、2,000 条跨历史日期的消息，其中 400 条保留草稿状态；总量、身份数和草稿比例不变。每组都分别记录完整列表和真实修改一百个不同身份后的 `changedSince` 增量，并断言增量包含这些身份，不能用空刷新或只换简单夹具证明达标。

最终服务器单 CPU 串行实测的后续五次中位数如下，三种模式均退出 0：

| 计时模式 | 当前消息完整列表 | 当前消息增量 | 混合历史完整列表 | 混合历史增量 |
| --- | ---: | ---: | ---: | ---: |
| 空区间 `plain` | 58.75 ms | 60.30 ms | 55.39 ms | 62.87 ms |
| 默认周期 `default` | 62.10 ms | 70.05 ms | 61.99 ms | 70.62 ms |
| 三十条实际终态 `history` | 63.19 ms | 73.83 ms | 83.61 ms | **117.81 ms** |

证据为 `/var/lib/role-workflow-proposals/artifacts/robust-feed-performance-final-plain.log`、`robust-feed-performance-final-default.log`、`robust-feed-performance-final-history.log`，保留真实查询计划和每次采样。历史模式当前完整列表中位数从优化前 622.11 ms 降至 63.19 ms。

**混合历史增量 117.81 ms 未达到 100 ms 建议目标。** 有交集时仍完整读取历史差量，且增量同时比较历史与当前资格；没有为了达标截断历史、清空例外、改变时效、增加缓存、索引或数据库迁移。按本轮确认的收尾范围如实保留这一量级，不继续扩大优化。

## 全天被晨间等待覆盖时的开放时间

每天名义开放间隙短于早安十五分钟等待时，默认关闭区间会覆盖整个周期。周期有效等待已按全天关闭与真实提前结束例外计算；旧有限区间合并却把样本最后的结束点当成“几天后开放”。

`test/reply-window-next-open-robustness.test.ts` 的两个探针仅使用原有 `replyWindow` 对象与 `morningRunEnded` 回调。根代理在冻结的 `860ea880` 基线上执行，两项均红：实际返回 `1793492100000`，期望未知。日志为 `/var/lib/role-workflow-proposals/artifacts/robust-next-opening-red.log`。

得到红证据后只做最小修复：当名义关闭与晨间等待覆盖整个周期时，`opensAt` 只来自已知真实提前终态形成的下一段开放间隙；没有时省略原本就可选的字段。已知本次间隙仍按实际结束时刻开放、到下一关闭计划时刻关闭。动态、运行设置与健康的正常级别说明在未知时显示“下次开放待定”，不再回退计划 `openTime`；不新增字段或告警级别。运行设置原有生命周期和未保存门控保持不变。修复后的两项探针和原回归已纳入最终 647/647 通过的候选构建。
