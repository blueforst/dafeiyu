# 消息分级实现与集成说明

实现入口为 `src/reply-triage.ts`，管理接口为 `src/triage-routes.ts`，定向回归为 `test/reply-triage.test.ts`。本文件记录代码接口，不将尚未执行的服务器回归、真实样本复核或生产观察记为完成。

## 数据与设置

`ReplyTriage` 构造时注册独立迁移版本 9“回复分级与公平调度”。七页之后的多个提案同时实现，原提案中的暂定版本 8 由统一版本分配替换为 9。迁移添加 `messages.tier`、`tier_reason`、`merged_into`，队列及历史索引、骚扰冷却表 `triage_ignores`、滑动窗口表 `triage_text_hits`。命中表另存消息标识并以账号和消息标识去重，重算排队消息不会重复增加不同用户计数。新终态仍分配单调 `processed_seq`；过滤、合并、忽略正文不能因该游标进入记忆输入。

`triage` 设置包含普通时效（默认三小时）、刷量不同用户阈值（默认三人）、广告词、招呼词、精确公开 handle 名单和精确私信会话名单。公开 handle 去 `@` 并忽略大小写；私信会话标识保持原样，不做跨渠道身份映射。公开每日额度通过独立 `publicPerDay` 配置，默认 180。

刷量规范化采用 NFKC，剔除提及、链接、空白、标点与符号后小写，再取 SHA-256 的前十六字节；不足六个 Unicode 码点不参与。滑动窗口使用可靠的平台时间，迟到或超出一小时的旧消息不进入当期刷量计数。只含链接且不含广告关键词不会仅因链接被过滤。

## 主循环接入

1. 采集后使用 `triage.ingest(event, accountId, maxAgeHours)` 代替直接入库。遗忘和可靠来源检查继续由原 `Store.ingest` 执行。
2. 每轮调用 `refreshQueued(accountId,maxAgeHours)`，旧排队记录补分级，重点名单调整后也可重新计算。先统计全部命中再分级，避免旧消息处理次序影响刷量阈值。
3. `allowedChannels` 由主循环提供当前控制模式、小时计数、平台退避和消息／出站两种 unknown 检查。草稿模式仅不受发送次数限制，仍保留退避与 unknown 隔离。
4. `pending(limit,accountId,channels,maxAgeHours)` 只选可用通道，按优先级及平台时间排序；查询直接筛选有效候选，过期条目按至多 `limit × 9` 分批终结；大量过期优先消息不会阻挡新鲜普通消息，每次最多读取 `limit × 10` 条。待重写草稿优先于普通分级，明确的管理员重写不会再次被原广告或忽略规则吞掉。
5. 生成前调用 `merge(row,accountId)`，以返回的新 `row` 为唯一目标，将 `context` 中先前消息按时间顺序加入当前对话。候选可能已由前一条合并，取走前继续检查数据库当前状态；合并模块也会重新读取当前状态。空会话标识、不可靠时间和管理员重写消息不参与合并。
6. 开始生成时调用 `consumed(id)`，清除管理员重排的一次过滤旁路。模型跳过结果调用 `recordSkip(event,accountId,category)`；类别说明与可选字段由共用模型解析接入。骚扰标签和忽略原因只用于本地调度，不传给记忆摘要。
7. 公开回复和早晚安帖子提交前检查 `dailyCount(accountId)`。统计北京时间自然日内已确认、提交中与未知出站，兼容旧消息并避免与已有出站重复计数；取消和平台拒绝不计本提案的每日额度。每日额度耗尽不会写入平台退避键。

重新排队为数据库操作，不访问浏览器或模型。已过滤、已合并、被忽略和普通失败消息可按管理员操作重新进入队列；该次重排会保留明确原因并跳过原过滤误判。该操作仍受可靠时间、额度、平台退避、未知出站和草稿审核约束；发送中、结果未知或已有不可重发冻结出站记录会返回冲突。

健康观察使用 `healthQueue(accountId,maxAgeHours)` 只读统计可处理的排队与已批准消息。排队条件与实际 `pending()` 共用同一 SQL 条件，包括分级时效、忽略、人工重排／重写和遗忘范围；已批准消息依显式批准及主循环原有最大时效判断。该接口不重分级、不清理过期行，也不更改游标或控制状态。

## 管理接口

所有路由复用应用现有管理鉴权及写请求标记：

| 接口 | 用途 |
| --- | --- |
| `GET /api/triage/summary` | 当前账号队列各级数量和最早时间、当日过滤／合并／忽略及原因、公开每日计数 |
| `GET /api/triage/ignores` | 当前生效的忽略记录，不返回正文 |
| `DELETE /api/triage/ignores` | `{userId,channel}` 解除当前账号的忽略与历史骚扰计数 |
| `POST /api/messages/:id/requeue` | 重新排队，拒绝未知或发送中状态 |
| `GET /api/triage/settings` | 可选：读取分级设置与独立修订号 |
| `PUT /api/triage/settings` | 可选：携带 `{settings,revision}` 保存，不恢复处理 |

常规日志仅保存关联 ID、账号／渠道、类别和计数，不记录正文。汇总接口是只读数据库查询，不隐式采集平台、调用模型或改变业务控制状态。

## 验证边界

定向回归覆盖规则顺序、精确重点名单、广告与同文刷量、滑动窗口、名单变化、旧排队迁移、优先级与时效、通道隔离、公开合并、骚扰到期和手动解除、北京时间每日额度及拒绝未知状态重排。构建和全部自动化回归由主代理在服务器独立 staging 执行，最终结果以本轮实施报告为准。脱敏历史消息回放的人工误判复核、生产发布和一天观察仍须各自留下证据，不能由合成样本通过替代。
