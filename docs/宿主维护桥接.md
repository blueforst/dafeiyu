# 宿主维护桥接

`deploy/maintenance-helper.py` 由宿主 systemd 每分钟读取固定请求及备份计划，独立于 app 的主循环和全局暂停。生产健康检查只有现有 `role-monitor.timer` 一个五分钟调度来源；该 timer 的 service 改为调用 helper 的 `--health-source` 固定入口。helper 不执行请求中的命令、路径、脚本或 systemd 服务名。证书续期仍由现有 `role-cert-renew.timer` 负责。

## 固定目录与权限

- 宿主数据根目录：`/var/lib/role-workflow`。
- app 可写请求目录：`maintenance/requests`；app 不可写其父目录。
- app 只读结果目录：`maintenance/results`；宿主独占计划 `maintenance/plans.json` 与 `helper.lock`。
- 宿主读取固定数据库 `app/workflow.sqlite`，备份固定写入 `backups`。

安装前建立 `role-maintenance` 系统组。请求目录应由 root 所有、该组可写，例如 `root:role-maintenance 0770`；结果目录由 root 所有、该组只读，例如 `root:role-maintenance 0750`。app 以附加组访问两个独立挂载；请求挂载可写，结果挂载 `:ro`。不要把整个 maintenance 父目录、宿主根目录或 Docker socket 挂入 app。

将新 maintenance service/timer 安装到 systemd 后启用 `role-maintenance.timer`。把 `deploy/role-monitor-health-source.service.example` 作为 `role-monitor.service` 的配置参考，令原 `role-monitor.timer` 继续每五分钟调用该 service。不要新增第二个健康 timer；不修改 `role-cert-renew.service/timer`。生产 helper 的常规 `due()` 不调度健康任务。

每个新的健康实例固定执行已有 `deploy/monitor.py` 一次，并投影容器状态、面板可达性、证书剩余时间等固定字段，不透传 monitor 中完整 status/config。外部 timer 入口不持有全局维护锁，手工入口和外部入口共用规范实例文件锁，锁内再次检查结果，防止并发重复检查。宿主每五分钟仍可记录 app 不可达。

健康计划的开关由 production-only `SystemdHealthAdapter` 执行字面命令 `systemctl enable --now role-monitor.timer` 或 `systemctl disable --now role-monitor.timer`；仅接受布尔值，成功后才保存计划。由于 maintenance service 使用 `ProtectSystem=strict`，安装时须预建 `/etc/systemd/system/timers.target.wants` 并按示例只对该目录增加 `ReadWritePaths`。请求不能选择 unit，证书单元不在任何命令分支内。隔离根目录强制 `SimulationHealthAdapter`，不执行生产 systemctl 或 monitor。`results/plans.json` 明确展示 source 与 adapterState；未验证的初始生产开关状态显示 unverified，配置成功后显示 applied。

以上是安装说明；代码存在本身不代表已安装或验收。当前生产已在用户授权的 0.1.15 发布中安装桥接，验证真实健康回执、false／true 开关、五分钟自动新实例，以及原证书常规到期检查成功且证书未变化，见[宿主维护发布记录](发布记录/2026-10-28-0.1.15-宿主维护.md)。实际故障演练与新证书签发若有需要，仍须独立证据，不能用代码或模拟命令测试替代。

## 请求与回执

请求文件名为规范 UUID 加 `.json`，正文例：

```json
{"id":"21f4591e-5602-47b0-a452-8a0b4a491188","task":"backup","action":"run"}
```

备份计划例：

```json
{"id":"d35a3715-d110-4513-bde6-c160565599ca","task":"backup","action":"configure","enabled":true,"time":"02:30"}
```

health 配置只接受布尔 `enabled`，其周期固定五分钟；请求中的 service、unit 等额外字段一律拒绝。backup 时间使用北京时间 `HH:mm`。未知字段、额外命令或路径、非 UUID 文件名及符号链接均不会被执行；规范 UUID 的无效请求产生 rejected 回执。单个请求上限 4096 字节，每次最多读取 100 个请求。

宿主原子写入 `results/<UUID>.json`，状态为 completed、failed 或 rejected。请求 UUID 标识一次请求；执行实例另用稳定 `instanceId`：备份按北京时间日期、健康检查按五分钟时间片计算。手动与自动请求共享实例，任意多个请求 UUID 在同一实例内只执行一次。请求回执保留请求 `id` 并引用该 `instanceId`；`results/health-latest.json`、`backup-latest.json` 使用规范实例回执，`plans.json` 为计划只读镜像。配置保存只修改计划，不恢复业务。

## 备份及恢复边界

备份初始关闭，默认北京时间 02:30。启动后只补当天一次，不回放遗漏日期。单次执行允许在开关关闭时明确请求；当天手动完成后自动计划复用同一实例，不再创建第二份。SQLite 在线备份完成后执行 `PRAGMA integrity_check`，原子移入备份目录，保留最近七份。相同实例重启时复用并检查已有备份。

备份只包含业务 SQLite 数据库，不含面板设置、模型 Key、源码、浏览器 profile 或独立遗忘账本。恢复前暂停并排空工作流，保存现有独立遗忘账本，恢复配套数据库后启动时重放遗忘记录。不得使用旧库覆盖现有遗忘账本；配置和凭据需要独立准备。

## 隔离验收

所有自动化测试在服务器执行。`test/scheduler-host-helper.test.ts` 创建临时数据库与请求目录，通过 Python 的独立 `Maintenance(root, now)` 夹具控制日期；非生产 root 不访问实际面板、systemctl 或生产 monitor。CLI 的 `--root` 仅用于独立验收，不可通过请求指定。覆盖默认关闭、单一健康来源、固定 timer 开关命令、隔离 adapter、防任意 unit、外部/手动并发实例锁、敏感字段投影、非法字段与符号链接、备份完整性、UUID 去重、七份保留及跨日只补一次。

服务器七页 staging 可使用 `role-maintenance-staging.service.example` 与 `.timer.example`，分别安装为 `role-maintenance-seven-staging.service`、`role-maintenance-seven-staging.timer`。其固定根目录为 `/var/lib/role-workflow-seven`，代码目录为 `/srv/role-workflow-seven`，附加组 GID 1000 与隔离 app 一致。请求目录 `root:1000 0770`，结果目录 `root:1000 0750`；app 只读挂载结果。该单元与生产 monitor、backup、certificate timer 无关。验收后可停用并删除这两个隔离单元，保留日志证据。

非生产 root 的健康结果有意不探测生产地址或运行生产 monitor，因此结果中“面板不可达”用于验证宿主在 app 不可用时仍能完成检查；不能将此状态当作生产或 staging 真实可达性验收。
