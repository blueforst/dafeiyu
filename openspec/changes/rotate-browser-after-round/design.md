# 完整轮次后的自动浏览器恢复设计

## Context

现有BrowserResourceGuard在各操作前采样资源，prepare-round可在安全点执行context close／launch。默认内存阈值为上限75%，最长运行二十四小时；现有防抖为持续30秒、至少两次有效采样，采样计数间隔至少一秒，最小重启间隔五分钟、每小时最多两次。提交、回查、控制和人工接管期间不恢复上下文。

正式运行仍有精确审核后保留的旧unknown及已解锁Chat。它们既不能被重发或丢失，也使原恢复入口长期处于protected-session。此次用户授权把必要自动恢复移至完整轮末，并对这两类soft状态作有限维护例外。新hard状态及真实资源故障、失败与次数限制不被豁免。

本提案未运行OpenSpec CLI，本机及服务器均缺少该命令；根openspec/config.yaml真实存在，本次只手工核对四份产物的结构与一致性，不初始化其他仓库或安装CLI。

## Goals / Non-Goals

**Goals:** 必要时自动等待完整业务轮次收束，在busy释放前完成一次有界恢复；保持原意图、身份、原已接受Chat及频率保护，成功后正常安排下一轮，失败安全暂停。

**Non-Goals:** 不增加外部定时任务或一次手工重启流程，不升级浏览器内核，不重建profile，不改变模型、人设、时段或发送额度；不清除unknown、自动接受额外请求、绕过私信解锁或发送测试内容。

## Decisions

### 1. 明确完整轮次，而不是在finally无条件恢复

新增内部Transport.finishRound及`POST /finish-round`。轮次顺序为：

1. prepare-round采样、区分保护及判定业务准入，不执行context close／launch。
2. 原回查、公开与私信采集、接受流程、queue、上下文／生成／send、整理及scheduler按原顺序全部await。
3. 只有常规业务路径完整收束，且控制仍running、控制修订未变、signal未abort时，进入finish-round维护阶段。
4. 等待该串行RPC真实收束后再结束轮次记录、采样健康并释放busy，之后按原间隔安排下一轮。

因hard门禁、异常、abort或其他early return未走完链路时，不调用finish-round，也不在finally补做。各采集阶段按原预算正常返回的partial结果仍据实保留，不能改判来源成功；任何已开始的异步操作都必须退出后才能认定维护安全点。手工业务任务不能自行伪造一个完整主循环轮末。

应用busy在此用于保留整轮互斥，不代表仍有未完成业务。只有本轮完整完成标识可以授予轮末安全点，不能先清busy来绕过active-round保护，也不能把维护RPC自身误判成另一项在途业务而永远无法恢复。

### 2. prepare的有限soft准入与finish的再次判断

仅在明确allowSessionRecovery策略生效，且保护集合只含有效精确reviewed旧unknown、已解锁Chat等soft项时，prepare不因临界内存提前fault／businessBlocked，允许本轮完整走到轮末。它改变的是本次已授权维护路径的有限准入，不是对之后所有临界压力的持续放行承诺。

以下仍为hard保护：新unknown、sending／submitting、私信接受意图未收束、needs-human／解锁待人工、人工接管、来源不明的编辑中内容、正在恢复及其他在途浏览器操作。新的hard unknown在临界压力下仍只回查并early return，不执行finish-round。真实故障、恢复失败、不可确认资源及恢复预算不得被allowSessionRecovery清除。

finish-round在浏览器serial锁内重新采样与核对，不复用轮前的“安全”结论。若本轮产生新hard状态，就只返回被保护延后，不关闭上下文。若压力已消退且未到运行时长阈值，就返回无需恢复，不为完成任务计数而重启。

### 3. 精确审核仅允许这一条旧项的维护例外

应用依据现有UnknownReviews和冻结指纹生成本轮审核集合；浏览器使用已鉴权RPC及自身journal／接受状态共同核对。不能仅凭客户端`reviewed=true`或一个允许布尔值忽略所有unsettled项。

审核仍须同账号、同public／reply对象、相同原消息与outbox及有效冻结指纹。原unknown、正文、目标、提交时间、回执、source唯一约束、计数与自动回查不变。原来缺失的历史journal不补造；已有journal及原意图逐项保留。未被该精确审核覆盖的应用或浏览器unknown、孤立意图、提交中项和未收束私信接受均阻止恢复。

该例外仅影响本次允许的维护；不能重排原来源、制造平台回执、恢复旧cancelled、跳过新unknown或推广成永久全账号许可。撤销、指纹变化或新的保护状态必须使维护资格失效。

### 4. 使用现有Guard恢复一次，并保持频率账本

实际恢复仍由BrowserResourceGuard调用现有内部restart依赖完成context.close、同profile的launch及页面恢复，不执行Docker重启、不删除设备预设或任何业务数据。内存持续至少30秒且有至少两次有效采样才触发；单次尖峰或过密重复采样不计成资格。运行时长阈值沿用现有设置。

最小五分钟间隔、每小时最多两次和恢复后压力观察沿用原策略；context重新launch不能清空同一Guard的频率历史。达到预算、短期压力复发或已锁定恢复故障时，不通过换请求ID、重建Guard或立即重试绕过限制，按原安全暂停／告警语义收束。

### 5. 同账号及原已接受Chat必须真实恢复

关闭前保存本轮已验证的账号身份，以及正常私信采集选定的一个可靠已接受Chat恢复对象，绑定原会话、自身与对端身份；只有已确认接受、实际可读且正确composer可编辑的对象才可用于验证。对象保存最多三条消息摘要，恢复后至少一条完全匹配；不声称验证全部历史会话。未收束接受、PIN／密码／人工提示及未绑定持久意图的草稿不构成安全点。

launch后先重新核对同一工作账号已登录、无身份切换或受限／needs-human，再按原生平台页面契约重新打开原已接受会话，验证实际消息可读、归属一致、请求接受提示未返回，且唯一正确会话composer可见、启用、可编辑。不能用普通收件箱empty、首页登录成功、一个通用输入框或缓存chat-unlocked标记代替该证据。

验证不发私信、不添加字符试发、不调用模型，也不自动接受请求或处理PIN。选定会话的证据缺失或恢复后变锁，均不能报告成功；保留实际状态并安全暂停，不重复close／launch尝试“解锁”。成功只在账号及该原Chat对象都通过后计入恢复成功。

### 6. 控制竞争、超时和幂等

finish-round携带本轮标识、预期账号及精确审核集合，沿用浏览器鉴权和serial队列。应用本地记录controlRevision，浏览器在路由入口捕获requestedControlGeneration，控制请求到达即递增；两个代次分别在各端核对，不作为RPC字段传输。应用保持busy，防止下一轮或独立业务任务与维护重叠；浏览器在真正close前再次检查模式、保护和本次操作是否仍有效。

暂停／接管在关闭前到达时取消维护；若同一次关闭已经开始，则只收束该次尝试并服从最新控制，不启动第二次恢复或下一轮业务。客户端abort／超时不等于服务端操作已经结束；serial不得提前释放给下一次维护，应用安全暂停并保留未收束标识。相同轮次／维护标识重入只能返回原结果或继续等待原尝试，不能第二次close。

恢复失败只记录一个有界尝试并安全暂停；不让finally、看门狗或后续自动轮次立即重复restart。管理员之后显式恢复沿现有流程重新检查，不自动清除故障或次数账本。

### 7. 观测以实际阶段为准

健康与日志区分待完整轮末、soft例外资格、hard保护延后、压力观察、恢复中、账号／Chat验证、完成和失败。保留轮次关联、原因、前后内存、次数及阶段耗时，不写私信正文、认证材料或解密内容。

prepare准入和finish结果各自从新鲜判断产生，health缓存businessBlocked可能被其他操作改写，不能用它单独证明某次临界业务被允许或恢复成功。维护失败不能无条件记录本轮completed；轮次结果与维护阶段一起反映失败或控制取消。

## Risks / Trade-offs

- 轮末恢复让已解锁Chat失去内存状态 → 必须绑定原已接受会话做真实可读／可编辑验证，失败暂停，不用empty inbox或反复restart掩盖。
- soft临界准入期间资源仍可能继续增加 → 只允许明确策略且无hard保护的完整轮次，finish再次采样，频率与真实故障限制保持，不承诺临界下业务永远不中断。
- 轮中新增unknown或接管 → 轮末重新核对，取消本次恢复，原意图只回查且不重发。
- 超时后服务端仍执行 → 保留serial与同次标识，安全暂停而非发第二个恢复请求。
- 历史审核被误解为发送成功 → 原状态及冻结数据不变，维护例外和发送回执分别展示。

## Migration Plan

预期无需新数据库迁移，沿用schema14、同profile、设备及journal。内部RPC与Guard行为成对部署；不支持轮末协议或版本不匹配时不退回轮前强制重启，保持待恢复／原安全暂停规则并给出诊断。

先在服务器独立环境完成类型、构建、完整适用单元与原生DOM／组合回归，再记录成对源码、镜像、回退及运行读回。正式环境用自然满足的资源条件验证一次自动轮末恢复，不降低阈值制造成功，不为验收发送内容或新增模型检查；维护自身费用应为零，正常业务调用另行计量。

回退恢复前一成对版本并保留业务库、审核和journal。旧代码会恢复原资源恢复时机及保护，不能把回退称为撤销审核或还原已关闭的内存会话；若实际Chat未恢复，继续暂停并保留人工处理原因。

## Open Questions

已确认这是必要时自动执行的程序行为，不是一轮手动操作。具体实际Chat恢复证据及生产压力条件须在实施时取证；未取得证据的任务保持未完成，不用既有0.1.28.7正常轮次或CLI产物存在替代新功能验收。
