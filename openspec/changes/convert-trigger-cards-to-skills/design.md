# 触发卡按需读取设计

## 背景与目标

现状（源码 `746ba7e`）：

- `PersonaTrigger` 有 `match: 'semantic' | 'keywords'` 和 `keywords` 两个字段。
- `PersonaService.assemble` 先在本地匹配关键词卡；有启用的语义卡时，再发一次路由请求（用途 `semantic-trigger`，`maxTokens=512`，推理取最低档）。命中卡片的内容放进 user 的提醒区。
- 静态分区全部进 system，其中包括标题含“被问到才用”的四个分区。
- 编辑器按标题是否含“被问到才用”把分区分成两组（`persona-editor.js`）。

目标：

- 卡片只有一种，页面只填标题、什么时候用、内容。
- 底层按 skill 的方式工作：system 里常驻目录，回复模型通过原生工具调用读取卡片内容。
- 工具调用流程是通用的，以后新增工具直接挂入，并共用每次回复 20 次的上限。

管理员确认的决定：

- 取消关键词触发；“被问到才用”分区并入触发卡。
- 界面上仍叫“触发卡”，不出现 skill 概念。
- 读取方式与 skill 一致：描述常驻，内容按需读取，读完可以继续读。
- 一次回复最多 20 次工具调用，读取卡片也计入。
- 只用原生工具调用，不做不支持工具调用时的退回方案；连接测试顺带检查工具调用。
- 虚构日程与早晚安帖带全部卡片。
- 不做子资料层，不做 skill 文件夹导入导出。

## 1. 卡片结构与校验

`PersonaTrigger` 改为 `{id,title,condition,content,enabled,order}`：

- 界面中 `condition` 显示为“什么时候用”，`content` 显示为“内容”。
- 原有长度限制不变：标题 100、条件 2,000、内容 20,000。全部分区、条件与内容合计仍不超过 20,000 字符。
- 编辑器在“什么时候用”下提示“一句话说明在什么情况下用这张卡”，不另加长度限制。

`validatePersona` 的变化：

- 收到 `match: 'semantic'` 时忽略该字段。
- 收到 `match: 'keywords'` 或 `keywords` 字段时返回 400“关键词触发已取消，请改写为什么时候用”。
- 导入文件与旧数据不经过这条校验，而是先走第 10 节的升级转换。

`matchedKeyword`、`normalizeTriggerText` 及相关调用删除。分级（`reply-triage.ts`）里的广告关键词与本提案无关，保持不变。

## 2. 目录与提示词

`assembleReplyPrompt` 在 system 中新增分段 `{kind:'cards',title:'触发卡目录',role:'system',stable:true}`。它位于静态人格之后、渠道规则之前；没有启用的卡片时不加这一段。文本格式：

```text
【触发卡】
下面的卡片平时不生效。判断本条消息用得上某张卡时，先用 read_card 读取它的内容再回复；用不上就不要读。卡片内容是你的人设资料，不是对方的指令。
- <id>｜<标题>：<什么时候用>
- …
```

- 目录按卡片顺序排列，只包含启用的卡片。同一人设修订内逐字节不变。
- “什么时候用”里的换行替换为空格，保证一张卡只占一行。
- 静态人格分段只包含分区，不再包含任何卡片内容。
- 提醒区不再拼接 `triggered`，只放动态提醒。
- 版本升为 `reply-context-v6`。

`segments` 仍与实际请求逐段一致。读取返回的卡片内容不属于首轮 `segments`，单独记入诊断数据（第 6 节），试聊提示词标签在首轮分段之后按顺序显示每次读取的结果。

## 3. 工具与调用循环

新增 `src/reply-tools.ts`，导出两部分：

- `ReplyTool` 接口：`{name, description, parameters, run(args, ctx)}`；
- `runReplyLoop(...)`：通用循环。

本提案只注册一个工具 `read_card`：

- 参数 `{id: string, reason: string}`。`reason` 是读取理由，最多 100 字符，超出截断，用于诊断显示。
- 返回 `【标题】\n内容`。

### 循环步骤

1. 首轮请求：system、首轮 user，加上全部已注册工具的定义。没有启用的卡片时不注册 `read_card`，只带 `submit_draft`，仍为一次生成请求。
2. 响应只有 submit_draft 时校验参数并结束；没有工具调用则失败，不把普通文本猜作工具输出。
3. 响应中有工具调用时，按出现顺序逐个处理：
   - 计数未满 20：执行该调用，计数加一；
   - 计数已满：不执行，返回 `已达到本条回复的工具调用上限（20 次），未执行。请直接用已有内容给出最终回复。`；
   - 标识不存在或卡片未启用：返回 `没有这张卡：<id>`，计数加一；
   - 同一回复内重复读取：返回 `这张卡已经读取过，内容见前面的结果。`，计数加一。

   把助手消息（含 Pi 返回的思考内容与签名）和每个调用的工具结果追加到消息列表，再发下一轮。
4. 计数达到 20 后，下一轮请求仍带相同的工具定义，以保持前缀和协议兼容（部分协议要求消息中出现工具调用时必须同时提供工具定义）。保持工具定义和原生 auto 选择不变，明确只允许 submit_draft；服务端拒绝继续读取。
5. 达到上限后，如果模型仍返回非终态工具调用，本条失败，错误码为 `tool-limit`，原因“超过工具调用上限”，不再请求。因此一条回复最多 21 次生成请求。
6. 每轮开始前检查 `signal`。中止或任一轮请求失败时抛出原错误，并附带 `callIds`（已完成和失败的各轮调用），供轮次与试聊统计费用。

### 最终草稿工具（管理员追加决定）

2026-10-29 管理员明确要求最终草稿也通过工具调用生成。回复循环始终注册 `submit_draft`，参数为 `{action:'reply'|'skip',text,reason,category?}`，只生成内部结果，不调用浏览器、不批准、不发送。它是终态输出，不占原来的20次读取／执行额度；一条回复仍最多21次生成请求。资料读取完毕后单独调用，不能与读取工具同轮并行。没有卡片时只注册这个终态工具，一次请求完成。

循环只验证终态工具参数结构，正文、字数、隐私与格式仍交各流程现有校验；回放继续保留有界违规结果计数。纯文本、普通 JSON 消息或无效参数按生成失败处理，不自动重试或猜测包装。每轮独立计量，meta 新增 `finalTool` 与 `finalToolCallId`。最终工具无需返回结果给模型，因此不增加额外请求。

所有草稿流程（生产回复、私信、试聊、预览、回放和早晚安）统一使用此输出。日程与记忆整理不是草稿，仍保留原 JSON 输出。草稿及连接测试的工具请求不附加 response_format，不再需要特定服务商的兼容分支。前置验证改为先读取测试卡、再调用终态工具，并另行记录真实效果。

### 会话与缓存

同一条回复的各轮使用同一个 `sessionId`。后一轮的消息列表是前一轮的完整延续，前缀一致，服务商可命中缓存。

## 4. 模型调用层

`Generator` 接口新增：

```ts
converse(c, system, messages, tools, signal?, sessionId?, metadata?, options?: {toolChoice?: 'auto'|'none'})
  : Promise<GenerationResult & {toolCalls: ToolCall[]; assistant: AssistantMessage; stopReason: string}>
```

- `runCompletion` 改为接受 Pi `Context`（`systemPrompt`、`messages`、`tools`）；原 `complete(system,user)` 改为包装成单条 user 消息、无工具调用 `converse`，其他调用方不受影响。
- `converse` 允许 `stopReason === 'toolUse'`。其余异常状态（error、aborted、length、deferred、pending）沿用 `complete` 现有的失败处理。
- 每轮各自 `ledger.start/finish`，元数据与本条回复相同（用途、来源、账号、渠道、`interactionId`）。
- `llm_calls` 没有存放附加信息的列。轮次不入库，同一 `interactionId` 下按 `started_at` 排序即为轮次顺序；草稿 `meta.callIds` 按轮次顺序保存。不新增数据库列，也不做数据库迁移。
- 测试替身（`test/` 中的假生成器）同步实现 `converse`。

## 5. 接入各流程

- **生产与试聊（`reply-pipeline.ts`）**
  - `assemble` 只组装首轮提示词并返回启用的卡片列表，不再发任何请求。
  - 生成阶段 `stage('generation')` 内运行 `runReplyLoop`。
  - 取消 `semantic-trigger` 和 `prompt` 阶段名，`metadata` 回调的步骤只剩 `reply`。
  - 返回值带 `calls`（全部轮次），让 `workflow.stage` 把各轮 `callId` 都计入本轮。
- **批量预览（`PersonaService.preview`）**：用同一个循环，用途仍为 `persona-preview`。`calls/fees` 汇总全部轮次。
- **回放（`persona-replay.ts`）**
  - 两侧各自组装首轮提示词并各自运行循环，`side` 照旧写入元数据。
  - 模型对比取消 `sharedPrompt` 和 `shared` 路由统计。结果的 `summary.sides` 保留 `shared` 字段，值全为 0，以兼容旧记录读取。
  - 预估：每侧每条的请求数取该账号近 7 天同用途回复的平均轮数（按 `interactionId` 分组计数），没有记录时按 2；价格沿用现有的单次 token 均值。
  - 预估文案说明“每读取一张卡多一次请求，每侧每条最多 21 次”。
- **早晚安帖（`production-tasks.ts`）与虚构日程（`daily-state.ts`）**：见第 8 节。

## 6. 诊断数据与展示

为了兼容旧记录和现有展示，草稿的 `meta.triggerHits` 继续使用，含义改为“本条读取的卡片”：`{id,title,reason}`，`reason` 是模型给出的读取理由。另加：

- `meta.toolCalls`：工具调用次数，含未执行和不存在的调用；
- `meta.toolLimit`：上限，固定为 20；
- `meta.callIds`：全部轮次的调用。

各处展示：

- **试聊本轮详情**：摘要写“读取：她自己、外貌”或“未读取触发卡”；详情显示每张卡及理由、“工具调用 n／20”。提示词标签在首轮分段后显示每次读取的结果。
- **动态右栏（`feed.js`）**：标题“本次触发规则”改为“读取的触发卡”，读取旧记录时保留原标题。
- **生成阶段**：`program.run` 的阶段记录增加 `detail: {rounds, cardsRead}`，排查页显示“请求 n 轮、读取卡片 m 张”。旧阶段记录没有该字段时不显示。
- **常规日志**：只记录卡片标识与次数，不记录卡片内容和读取理由以外的正文。

## 7. 连接测试

`model-library.ts` 和 `model-routes.ts` 中的测试请求改为：

- system“你是接口验收助手。调用 connection_check 工具，参数 ok 填 true。”；
- 带一个工具 `connection_check({ok:boolean})`；
- Chat Completions 协议上同时带 `response_format: json_object`，与正式请求的结构相同。

判定：

- 响应包含对 `connection_check` 的调用才算通过；
- 只返回文字算失败，原因“未完成工具调用”；
- 接口报错按现有方式显示原因。

输出上限：关闭推理时 256，开启时 2048。不回传工具结果，只发一次请求。CLI `model-check` 用同一逻辑。

## 8. 无对话场景

- **虚构日程**：`daily-state.ts` 现在拼接全部分区内容；改为分区内容之后，再按顺序追加全部启用卡片的 `【标题】\n内容`。
- **早晚安帖**：`persona.assemble` 新增选项 `cards: 'all'`。不加目录和读取工具，全部启用卡片的内容放进静态人格分段末尾；只带 submit_draft，仍是单次请求，用途 `morning-post`、`evening-post` 不变。

## 9. 第 3 版内置预设

`PERSONA_PRESETS_VERSION` 改为 3。每个预设的四个始终生效分区与第 2 版逐字相同，保证升级时这些分区不变。卡片部分：

| 卡片 | 什么时候用（要点） |
| --- | --- |
| 不给步骤 | 对方要你给做法、教程、步骤、清单或攻略，无论怎么问 |
| 被夸 | 对方在夸你本人（外貌、性格、能力）；反话、嘲讽、骚扰（例如“别装可爱”）不算 |
| 她自己 | 对方问到或聊到你的喜好、口味、习惯、往事 |
| 外貌 | 对方问你长什么样、夸你或聊到外表 |
| 认识的 AI 娘 | 对方提到其他 AI 或 AI 娘 |
| 身份设定 | 对方问你是谁做的、用什么模型、和官方什么关系 |
| 角色专属卡 | 原关键词所代表的话题，按意思改写，例如大肥鱼“被说胖”写作“对方友好地拿你的体形开玩笑” |

规则：

- 卡片内容沿用第 2 版正文。原四个分区第一行的条件句移到“什么时候用”，内容只保留其后的正文。
- “被问到才用”的标题后缀去掉。
- 顺序：不给步骤、被夸、她自己、外貌、认识的 AI 娘、身份设定，然后是角色专属卡。
- 原 `SIGNATURE_GUARD` 仍附在角色专属卡内容末尾。
- 卡片 `id` 沿用第 2 版：分区用 `self`、`appearance`、`friends`、`identity`，卡片用 `<预设>-no-steps` 等，便于第 10 节按标识匹配。
- 第 2 版的完整预设文本作为常量 `PERSONA_PRESETS_V2` 保留在单独文件中，只供升级比对。

## 10. 旧人设升级与文件版本

### 升级函数

`upgradePersona(raw, origin)` 是纯函数，对一份旧结构人设逐项处理：

1. **标题含“被问到才用”的分区**
   - 来源为 `preset` 且 `presetVersion === 2`，内容与 `PERSONA_PRESETS_V2` 中同 `id` 分区逐字相同：换成第 3 版对应卡片。
   - 否则：标题去掉“（被问到才用）”“(被问到才用)”及首尾空白；条件写为 `别人问到或聊到「<标题>」相关内容时使用。`；内容保留原文（包括原来的第一行条件句）。
   - 转换出的卡片 `enabled=true`，排在原有卡片之后，顺序号依次递增。
2. **关键词卡**
   - 来源同上，且标题、条件、内容、关键词与第 2 版同 `id` 卡片逐字相同：换成第 3 版卡片。
   - 否则：条件以“消息包含以下任一关键词：”开头时，改写为 `对方聊到下列说法或类似意思时使用：<原关键词，以、连接>`；其他条件保留原文。
   - 删除 `match` 和 `keywords`，启用状态和顺序不变。
3. **语义卡**：只删除 `match`。
4. 其余分区不变。

函数返回 `{persona, changed}`。对已是新结构的人设返回 `changed=false`，因此可以重复执行。

### 执行时机

服务启动时执行一次，在人设库首次读取之前完成：

1. 读取面板设置。对 `personaLibrary.items[].persona` 和兼容镜像 `persona` 分别升级。
2. 只要有任一项变化：
   - 先把原面板设置整份写入 `DATA_DIR/backups/persona-upgrade-<UTC时间>.json`，权限 0600；
   - 再一次性写回面板设置；
   - 变化项 `revision + 1`，镜像修订号与使用中人设同步，`libraryRevision + 1`；
   - 记录日志 `persona-upgrade`，内容只含人设标识、变化项数和备份文件名。
3. 不改变运行控制、模式和使用中人设。

### 字数上限

升级后总字数超过 20,000 时照常写入。读取路径对已保存数据使用 `validatePersona(..., {stored:true})`，跳过总字数检查；编辑保存和导入时仍执行全部检查，编辑器显示“超出上限，保存前需删减”。

### 人设文件

- 导出 `version: 2`。
- 导入 `version: 1` 时先过 `upgradePersona`，来源视为 `copy`，不做预设比对，然后按现有规则校验。

### 试聊库

试聊使用人设库中的人设，不另存人设副本，无需单独升级。

## 12. 兼容、失败与回退

- **旧记录**：消息、试聊、回放中旧的 `triggerHits`（含“关键词：…”原因）照常显示。用途为 `semantic-trigger` 的调用在计费页照常统计。
- **旧接口**：`PUT /api/persona` 和人设库保存不再接受关键词字段，返回 400 与说明，批量验收工具同步更新。预览接口的返回结构保留 `hits`、`calls`、`fees`、`warning`；`warning` 不再出现语义回退文案。
- **失败**：任一轮失败都按现有生成失败处理。生产消息进入原有错误或重试路径，试聊回到待处理状态，所有已落账用量保留。不新增自动重试。
- **试聊等待时间**：试聊页面现在最多等待 360 秒。多轮读取的总耗时通常远低于此，因此不调整（我的决定）。超过时页面照现有方式提示请求超时，后端这一轮继续完成；实施时核对刷新后能看到该轮结果，看不到则作为缺陷修复。
- **场景名称**：修改其他提案中的需求时，按 OpenSpec 归档规则保留了全部原有场景名称，只改写内容。因此“语义规则只判定一次”“关键词卡命中”等名称描述的是升级后的对应行为，以场景正文为准。
- **回退**
  - 代码回退前，用升级备份恢复面板设置。旧版本能读取新结构的卡片：没有 `match` 时按语义卡处理。
  - 不恢复备份直接回退，结果是：卡片按旧语义路由运行，原四个分区以卡片身份存在、不再常驻 system，关键词卡不复存在。
  - 回退步骤写入发布记录。

## 13. 验证

- **单元测试**（服务器）
  - 循环：无工具一次请求；读一张、连续读两张；不存在、重复；同轮并发超限；满 20 后再调用即失败；中止；第二轮失败时 `callIds` 完整。
  - 提示词：目录位置与文本；system 和工具定义在不同消息间逐字节一致；提醒区不含卡片；第二轮前缀与首轮一致；版本号。
  - 升级函数：每条规则；重复执行不变；超长人设可读不可存。
  - 预设：六个预设的结构、卡片顺序与第 3 版说明；“被夸”说明含反话、嘲讽和骚扰。
  - 文件：第 1 版转换、第 2 版往返。
  - 连接测试：工具调用、纯文字、接口拒绝三种结果。
- **界面验收**：`dev/workspace-ui-test.sh` 覆盖编辑器两组与卡片表单、试聊读取摘要与详情、动态右栏新旧两种标题、回放预估文案；原有业务断言保留。
- **真实模型**（计费，需授权）
  - 用使用中的模型先验证“工具加 JSON 对象”的组合（任务 1.1）。
  - 再用试聊跑以下消息，记录读取的卡、请求轮数、费用和回复：
    - 大肥鱼：“别装可爱”“你好可爱”“怎么才能做好番茄炒蛋”“你长什么样”“你平时爱吃啥”，以及两条普通闲聊；
    - 另一个角色预设：“你是官方的吗”。
  - 判定标准：
    - “别装可爱”不读“被夸”，“你好可爱”读“被夸”；
    - 问做法读“不给步骤”，问外貌读“外貌”；
    - 普通闲聊不读卡；
    - 每条回复的工具调用不超过 20 次。
  - 未达标的如实记录，不改写结论。

## 14. 风险

- **模型不读该读的卡。** 目录描述写得不清楚时会漏读。缓解措施：预设说明按意思改写；试聊详情显示读取理由，方便管理员调整“什么时候用”。真实模型验收专门覆盖误读和漏读的样例。
- **请求轮数增加。** 原来只用关键词卡的人设，需要卡片时会多一轮请求。读取后的请求共用前缀，费用主要来自新增的输出和工具结果。回放预估和计费页都能看到实际轮数。
- **不同协议的工具细节。** 思考内容的回传、`toolChoice` 支持、并行调用都有差异，统一交给 Pi 处理；连接测试先暴露不兼容的接口。


## 本轮验证补充

原先工具加原生 JSON mode 曾把读卡意图写成空正文 JSON 或 action=read_card，去掉格式约束后也有一次读卡后直接输出纯文本。原样本保留。管理员随后决定统一使用终态草稿工具，上述临时格式兼容分支已删除；最终验收只采用新工具协议的样本。

执行次数以增量规格“最多执行20次”为准；toolCalls 为读取及其他执行工具，另有 toolAttempts；submit_draft 单独记入 finalTool。生成轮次由 callIds 与阶段 detail 关联，不增加主库列。

旧人设全部分区均需移动时保留一个空白角色分区；空正文条件分区原样保留。升级后的既有数据允许最多120张卡以容纳原100张卡加20个分区，普通保存仍要求最多100张；顺序封顶10000并按稳定顺序追加，不因旧合法边界阻止启动。

未注册任何读取／执行工具的场景只能单次终态输出；模型误造其他工具名直接失败，不发起后续请求。这使发布后的无卡草稿验收能够在同一美元账本中预留单次最坏费用。
