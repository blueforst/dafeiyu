# 人设管理增量规格（触发卡按需读取）

## MODIFIED Requirements

### Requirement: 触发规则可视化管理

系统 MUST 允许管理员编辑触发卡的标题、“什么时候用”、内容、启用状态及顺序。人设编辑页 MUST 只分“始终生效”和“触发卡”两组，不得出现触发方式、关键词、skill 或工具调用等选项。只有本次回复实际读取的启用卡片内容进入该次请求；未读取或已关闭的卡片内容不得出现在请求中。

#### Scenario: 规则未命中或被关闭
- **WHEN** 某张卡片本次没有被读取，或已被管理员关闭
- **THEN** 本次回复的请求不包含它的内容；关闭的卡片也不出现在触发卡目录中

#### Scenario: 编辑一张卡片
- **WHEN** 管理员新建一张触发卡
- **THEN** 编辑区只有标题、什么时候用、内容三个输入项，以及启用开关和顺序调整

#### Scenario: 保存旧结构的卡片
- **WHEN** 接口收到带 `match: "keywords"` 或 `keywords` 字段的触发卡
- **THEN** 保存被拒绝并提示关键词触发已取消；人设文件导入则按旧人设升级规则转换

### Requirement: 内置人设预设

人设页人设模式的左栏 MUST 在“内置预设”分组中列出通用（默认）、大肥鱼、GPT 娘、Claude 娘、Kimi 娘、GLM 娘六个内置预设，选中后在主区只读显示其名称、一句话简介、全部分区和触发卡。预设 MUST 不能直接编辑、保存或设为使用中；管理员点击“以此新建”后，系统 MUST 在“我的人设”中新建一个内容相同、处于未使用状态的人设，之后按普通人设编辑、试聊、回放对比和保存。预设 MUST NOT 覆盖任何已有人设的内容。

每个预设 MUST 包含角色定义、说话风格、记忆与承诺、互动边界四个始终生效的分区，并且都包含一张“不给步骤”和一张“被夸”触发卡。五个角色预设 MUST 另含她自己、外貌、认识的 AI 娘、身份设定四张触发卡，不再以分区形式存在。每张预设卡片的“什么时候用” MUST 写明适用的意思而不是罗列字词；“被夸”卡 MUST 写明反话、嘲讽和骚扰不算夸。每个预设的说话风格 MUST 先写六个预设完全相同的通用写法，再写本预设自己的口吻，口吻写明公开回复的常用长度；角色梗 MUST 按对方是否聊到相关话题、近期往来里是否用过来约束，不写模型无法核对的“几条里一次”频率。五个角色预设 MUST 写明自己是网友二创的非官方角色、与对应公司无关，不冒充官方。

#### Scenario: 以预设新建但不启用
- **WHEN** 管理员选中内置预设“大肥鱼”并点击“以此新建”
- **THEN** “我的人设”中出现内容与预设相同的新人设，处于未使用状态；使用中人设和它的修订号不变

#### Scenario: 预设只读
- **WHEN** 管理员在左栏选中任一内置预设
- **THEN** 主区内容不可编辑，页头只有“以此新建”，没有保存、设为使用中和删除

#### Scenario: 修改后保存
- **WHEN** 管理员从“GLM 娘”新建人设，改动说话风格后保存
- **THEN** 系统保存改动后的内容，该人设修订号加一；内置预设“GLM 娘”保持原样

#### Scenario: 选用预设不增加判定调用
- **WHEN** 管理员从任一预设新建人设、不做修改并设为使用中，模型对一条普通闲聊没有读取任何卡片
- **THEN** 本条消息只有一次回复生成请求，没有单独的判定请求

#### Scenario: 被问是不是官方
- **WHEN** 使用从“Claude 娘”新建且未修改的人设时，用户问“你是 Anthropic 官方的吗”
- **THEN** 互动边界始终要求说明自己是网友二创的非官方角色、与 Anthropic 无关；“身份设定”卡的“什么时候用”覆盖这类问题

#### Scenario: 询问做法
- **WHEN** 使用从任一预设新建且未修改的人设，测试用户在试聊中问“怎么才能做好番茄炒蛋”
- **THEN** 模型读取“不给步骤”卡，其内容以工具结果进入请求，试聊本轮详情显示读取了“不给步骤”及理由

#### Scenario: 被问到才用的分区
- **WHEN** 管理员查看任一角色预设
- **THEN** 她自己、外貌、认识的 AI 娘、身份设定出现在“触发卡”组，各有一句“什么时候用”；“始终生效”组只有四个分区

#### Scenario: 比较两个预设的说话风格
- **WHEN** 管理员先后查看内置预设“大肥鱼”和“Claude 娘”的说话风格分区
- **THEN** 两者开头的通用写法完全相同，之后的口吻不同，且各自写明公开回复的常用长度

#### Scenario: 被夸
- **WHEN** 使用从任一预设新建且未修改的人设，用户说“你好可爱”，另一位用户说“别装可爱”
- **THEN** 前者读取“被夸”卡；后者不读取“被夸”卡。该卡的“什么时候用”写明对方在夸角色本人时才用，反话、嘲讽和骚扰不算

### Requirement: 提示词与命中结果预览

系统 MUST 在人设页试聊模式的本轮详情和提示词标签中展示每一轮的回复或跳过结果、读取的触发卡及模型给出的读取理由、工具调用次数、实际提示词分段及耗时，且不得展示密钥。

#### Scenario: 检查一次试聊
- **WHEN** 管理员查看一轮读取过两张卡片的试聊
- **THEN** 能分别检查静态分区、触发卡目录、读取的两张卡片及理由、日程、召回的记忆与当次上下文，并看到工具调用 2 次，且无密钥内容

## ADDED Requirements

### Requirement: 按需读取触发卡

回复生成 MUST 在 system 中提供全部启用触发卡的目录，每张卡写明标识、标题和“什么时候用”，并为模型提供读取卡片的工具。模型 MUST 能根据当前消息、对话、记忆和其他可见资料自行决定读取哪些卡片；读取的卡片内容以工具结果返回，模型读完一张后可以继续读取其他卡片。模型不读取卡片时，本条回复 MUST 只有一次生成请求，通过终态草稿工具生成。没有启用的触发卡时，请求不得携带读取工具。生产、试聊、回放和批量预览 MUST 使用同一套读取流程。

#### Scenario: 读取一张卡后回复
- **WHEN** 用户问“你平时爱吃什么”，人设带“她自己”卡
- **THEN** 模型读取“她自己”卡，系统把该卡内容作为工具结果返回，模型随后写出回复；本条共两次生成请求，诊断显示读取了“她自己”及理由

#### Scenario: 连续读取
- **WHEN** 模型读完“她自己”后，又判断还需要“认识的 AI 娘”
- **THEN** 系统继续返回第二张卡的内容，两张卡都计入本条回复的工具调用次数

#### Scenario: 没有启用卡片
- **WHEN** 人设没有任何启用的触发卡
- **THEN** 请求不带读取工具，system 中没有触发卡目录，本条只有一次生成请求

### Requirement: 回复工具调用上限

一次回复 MUST 最多执行 20 次工具调用。读取触发卡计入该次数，以后新增的工具也计入同一上限；通过 submit_draft 写出最终草稿不计入读取／执行额度。达到上限后，系统 MUST NOT 再执行读取或其他执行工具，并告知模型直接用已有内容调用 submit_draft；此后模型仍请求读取或其他执行工具时，本条回复按生成失败处理，不再继续请求。一次回复中同时发起的多个工具调用逐个计数，超出上限的部分不执行。

#### Scenario: 用满 20 次
- **WHEN** 模型在一条回复中已经执行了 20 次读取
- **THEN** 之后的工具请求不再执行，模型收到已达上限的说明并写出最终回复；本条最多 21 次生成请求

#### Scenario: 一次发起多个调用超过上限
- **WHEN** 已执行 19 次后，模型在同一轮同时请求读取 3 张卡
- **THEN** 只执行第一张，其余两个调用返回“已达上限、未执行”，计数停在 20

#### Scenario: 达到上限后仍要读取
- **WHEN** 达到上限并收到说明后，模型仍然请求工具
- **THEN** 本条回复失败，原因显示为超过工具调用上限，已产生的调用照常计费，不再发起请求

### Requirement: 读取异常处理

系统 MUST 校验每次读取请求：标识不存在或卡片未启用时，返回“没有这张卡”；同一条回复内重复读取同一张卡时，返回“已读取过”的说明而不再重复内容；这两种情况都计入工具调用次数。任一轮生成请求失败或被中止时，本条回复 MUST 按现有生成失败处理，不自动重试该轮，已落账的用量全部保留。

#### Scenario: 读取不存在的卡
- **WHEN** 模型请求读取一个目录中没有的标识
- **THEN** 工具结果说明没有这张卡，计数加一，模型可以继续读取其他卡或直接回复

#### Scenario: 第二轮请求失败
- **WHEN** 模型读取一张卡后，下一轮生成请求因服务商错误失败
- **THEN** 本条回复按生成失败处理，第一轮和失败那一轮的用量都出现在调用流水中

### Requirement: 无对话场景使用全部触发卡

虚构日程生成和早晚安帖生成 MUST 直接带上全部启用触发卡的内容，与始终生效分区一起作为人格资料，不提供读取工具、不产生读取请求；早晚安草稿只带 submit_draft，日程保留原输出。

#### Scenario: 生成当日日程
- **WHEN** 使用中人设带“她自己”卡，系统生成当日虚构日程
- **THEN** 传给模型的人格资料包含“她自己”卡的内容，本次只有一次请求

#### Scenario: 生成早安帖
- **WHEN** 系统按计划生成早安帖
- **THEN** 提示词包含全部启用触发卡的内容，请求不带读取工具

### Requirement: 旧人设升级

升级后系统 MUST 对人设库中的每个人设和兼容镜像执行一次性转换，转换前先备份原设置：
- 关键词卡转为普通触发卡，去掉关键词字段；原“什么时候用”是自动生成的“消息包含以下任一关键词：……”时，改写为“对方聊到下列说法或类似意思时使用：……”，否则保留原文；
- 标题含“被问到才用”的分区转为触发卡，标题去掉该后缀，“什么时候用”写为“别人问到或聊到「标题」相关内容时使用。”，内容保留原文；
- 来源为第 2 版预设、且与第 2 版预设内容完全相同的卡片和分区，换成第 3 版预设中对应的卡片；
- 已有语义卡只去掉触发方式字段，标题、条件和内容不变。

内容有变化的人设 MUST 修订号加一，使用中人设和运行控制 MUST 保持不变；重复执行 MUST NOT 再次改变内容或修订号。转换后总字数超过 20,000 字符的人设 MUST 仍可使用，管理员下次保存时才要求删减。

#### Scenario: 升级一个改过的预设人设
- **WHEN** 升级前有一个从第 2 版“大肥鱼”新建的人设，管理员只改过“外貌”分区
- **THEN** 升级后“外貌”成为触发卡并保留改过的内容；她自己、认识的 AI 娘、身份设定三个分区和全部关键词卡换成第 3 版预设的对应卡片；四个始终生效分区不变，修订号加一

#### Scenario: 升级自定义关键词卡
- **WHEN** 管理员自建了一张关键词为“猫、喵”的卡片
- **THEN** 升级后它成为普通触发卡，“什么时候用”包含“猫、喵”，内容不变

#### Scenario: 升级时业务暂停
- **WHEN** 升级时工作流处于暂停
- **THEN** 升级完成后仍保持暂停，不自动处理消息

#### Scenario: 重复启动
- **WHEN** 升级完成后服务再次重启
- **THEN** 人设内容和修订号不再变化

## REMOVED Requirements

### Requirement: LLM 语义触发判定

**Reason**: 单独的路由请求只看得到卡片条件，看不到卡片内容，而且只要有语义卡，每条消息都要多请求一次。改为回复模型在生成时按目录自行读取，见“按需读取触发卡”。

**Migration**: 不再产生用途为“语义触发”的路由请求；历史调用记录和消息详情中的旧命中原因照常显示。已有语义卡按“旧人设升级”保留标题、条件和内容。

### Requirement: 语义判定失败回退

**Reason**: 没有单独的判定步骤，也就没有“判定失败、退回静态规则”的分支。生成过程中的读取异常和请求失败改由“读取异常处理”规定。

**Migration**: 日志中不再出现 `semantic-fallback`，历史记录保留。

### Requirement: 关键词触发规则

**Reason**: 子串匹配误判和漏判都多，例如骚扰消息“别装可爱”命中了“被夸”卡，换个说法又漏判。管理员确认关键词触发意义不大。

**Migration**: 已有关键词卡按“旧人设升级”转为普通触发卡，关键词写进“什么时候用”；保存接口不再接受关键词字段。


## ADDED Requirements

### Requirement: 终态草稿工具

所有回复及早晚安草稿 MUST 由原生 submit_draft 工具提供 action、text、reason 及可选跳过类别；工具只生成内部草稿，不能批准或发送。系统 MUST 保留原有正文、字数、隐私、审核和发送校验。终态调用 MUST 单独出现，不得与读取工具并行，普通文本及 JSON 消息 MUST 按缺少终态调用失败，不自动重试。终态输出不占20次读取／执行额度，仍最多21次生成请求。

#### Scenario: 没有读取时直接提交草稿
- **WHEN** 一条消息无需读取人设卡
- **THEN** 一次请求调用 submit_draft 即形成内部草稿，后续校验与审核不变

#### Scenario: 读取后提交草稿
- **WHEN** 模型先读取一张卡再准备答复
- **THEN** 第二轮单独调用 submit_draft，二轮均计费，读取次数为一，终态调用另记

#### Scenario: 普通文本或并行提交
- **WHEN** 模型仅返回文本，或把 submit_draft 与 read_card 放在同一轮
- **THEN** 生成失败且保留已发生用量，不自动重发或提交平台
