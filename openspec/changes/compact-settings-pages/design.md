草图里标“示例”的用户、记忆、调用、次数和耗时是排版示意，不是生产数据。下文没有标注的内容由管理员确认；标注“（规划时决定）”的由规划者补充，管理员审阅时可以推翻。

## 1. 共用部分

### 1.1 样式（`style.css`、`settings-workspace.css`）

- `.settings-item-content` 保留 `max-width:1320px`。新增 `.ws-cols`：两列 `minmax(0,1fr)`，`gap:16px`，`≤1100px` 改单列。
- 新增 `.ws-card`：边框 `--ws-border`，圆角 12px，内边距 14px 18px；卡片标题行 `.ws-card-head`（标题加浅色说明）。
- 数字输入 `.ws-num`：宽 64px；带单位时 78px；时间输入 `.ws-time` 宽 74px。设置页内的 `input[type=number]`、`input[type=time]` 不再继承 `width:100%`。
- 开关 `.ws-switch` 用原生 `input[type=checkbox][role=switch]` 加样式，保持 `check()` 可测（规划时决定）。
- 统计条 `.ws-stats`：一行多格，竖线分隔，`≤860px` 两列。
- 行内操作 `.ws-row-actions`：默认 `visibility:hidden`。`tr:hover`、`tr:focus-within`、`tr.selected` 时可见。`@media(hover:none)` 下只认 `.selected`。用 `visibility` 而不是 `display`，列宽不跳。
- 空状态行 `.ws-empty-line`：一行内用 ✓ 列出多个“没有……”。

### 1.2 共用组件（`public/js/shell.js` 或 `view-utils.js`）

- `advanced(id, summary, ...content)`：返回 `details.ws-advanced`，`summary` 显示“高级设置”加浅色概要（各项当前值）。展开状态读写 `localStorage['ws:settings:advanced:'+id]`，读写都包在 try/catch 中，失败时按收起处理。内容中的输入归入所在页的未保存检查（`editorGuard` 的 dirty 计算包含它们）。
- `advancedDialog(id, title, ...content)`：给列表加详情的页（记忆、模型）用，页头放“高级设置”按钮，打开 `modal`，关闭前检查未保存修改。
- `fmtUsd(value)`：`null`、`undefined` 返回“—”。≥1 时保留两位小数；<1 时从第一个非零位起保留两位有效数字（0.04840811 → $0.048，0.0002454 → $0.00025，0.0011 → $0.0011）。返回的节点 `title` 为精确值。计费、健康日报、模型价格、任务历史统一使用（规划时决定）。
- `rowActions(...buttons)`：包一层 `.ws-row-actions`。触屏选中由行点击切换 `.selected`。

## 2. 模型

### 2.1 数据（`model-library.ts`、`settings.ts`）

- `LibraryProvider` 增加 `starred?: string[]`，即有序的模型 id 列表。
- `LibraryModel` 增加 `api?: PanelModel['api']`。
- `materialize()` 取 `model.api ?? provider.api`。
- **协议迁移**：读取模型库时，自定义服务商的每个模型若没有 `api`，就补成 `provider.api`。`provider.api` 原值保留在文件里，新代码不再读取，供回退旧版本使用；下一个版本再清理（规划时决定）。目录服务商不写 `model.api`，协议仍取 pi 目录。
- **星标接口**：`PUT /api/model/library/:key/stars`，请求体 `{revision, ids}`。
  - `ids` 去重后只保留该服务商已有的模型 id，按给定顺序保存，修订号加一。
  - 星标模型被刷新标为 `missing` 时仍保留。
  - 删除模型（手动添加的）时同时移出星标。
- **最近使用**：`GET /api/model` 的库视图中，每个模型增加 `lastUsedAt`。
  - 来源：`llm_calls` 中 `started_at >= now - 30 天`，按 `provider, model` 取 `max(started_at)`，所有用途都算。一次查询，结果按 `(provider.provider, model.id)` 匹配。
  - 多个自定义服务商有同名模型时都会标为最近使用（规划时决定，`llm_calls` 没有记录服务商 key）。
- **缓存价**：`ModelInfo.cost` 增加 `cacheRead`、`cacheWrite`，取自 pi `m.cost`。CommandCode 等未定价模型仍为 `costKnown:false`。
- **自定义接口拉取**：`discoverModels` 对自定义服务商不再依赖服务商协议。
  - 先发 OpenAI 兼容 `GET {base}/models`，失败再发 Anthropic 兼容 `GET {base}/v1/models`。两次合计仍受原 25 秒上限约束。
  - 成功的那一种决定新发现模型的默认 `api`：`openai-completions` 或 `anthropic-messages`。
  - 已存在模型的 `api` 不被刷新覆盖。
  - 两次都失败时，`fetchError` 写两种请求的失败原因。
- **添加与编辑接口**：
  - `POST /api/model/library` 对 `custom` 不再要求 `api`。
  - `PUT /api/model/library/:key` 收到 `api` 时忽略，不报错。
  - 模型参数 `PUT .../models/:id` 对自定义服务商接受 `api`，取值为 `CUSTOM_APIS` 之一。
  - 修改模型 `api` 时清除该模型的 `lastTest`。

  - 只渲染 `library.providers`，删除“可添加”目录列表。

- **服务商编辑窗口**：
  - 字段为名称、地址、Key（掩码占位，留空不改）。沿用现有“改主机必须重填 Key”的逻辑。
  - 左下角“删除服务商”。使用中时禁用，并写明原因。
  - 保存后关闭，并刷新库。
  - 原 `rename()` 和“更多”菜单合并进这里。
- **工具栏**：服务商名、“N 个模型”、搜索（宽 300px）、“刷新列表”、“手动添加模型”。
- **表格**：
  - 列：☆、拖动柄（只在星标块悬停时可见）、模型、上下文、价格、测试、行内操作。
  - 模型列后面跟灰色图标：灯泡（支持推理）、眼睛（支持看图），用 SVG 加 `<title>`；后面再跟“使用中”标签。
  - 价格单元格 `tabindex=0`，悬停或聚焦时显示提示框，内容为四项单价与“美元 / 每百万 token · 来自 pi 目录”。
  - 分块与排序：
    - 星标块按 `starred` 顺序；
    - 最近使用块按 `lastUsedAt` 降序；

  - 显示数量沿用每次 60 行加“显示更多模型”，只作用于“其他模型”块（规划时决定）。
- **拖动排序**：
  - 用原生 HTML5 拖放；放下后乐观更新，再调星标接口，失败时回滚并提示。
  - 键盘方式：星标行聚焦后，Alt+↑ / Alt+↓ 移动（规划时决定）。
- **模型编辑窗口**：
  - 只读信息块：接口协议（目录模型注“目录自带”）、上下文、价格、能力。
  - 可编辑：推理强度。自定义服务商的模型多一个协议下拉。
  - 手动添加窗口同样有协议下拉，默认取该服务商最近一次拉取成功的协议。没有拉取成功过时默认 `openai-completions`（规划时决定）。
- **删除的内容**：页头“刷新目录”“连接测试”“保存连接”；页面上的地址、协议、Key 输入框；“全部 / 已测试 / 未定价”筛选。
- 窄屏下，顶部选择器旁边放“添加”和“编辑”。

## 4. 消息时效合并（`reply-triage.ts`、`settings.ts`、`program.ts`、`app.ts`、`triage-settings.js`）

- **语义**：唯一的“消息时效”就是现有 `program.maxAgeHours`（范围 1–48）。
  - `normalizeTriageSettings` 不再产出 `normalMaxAgeHours`。
  - 分级判断、`ageSql`、动态过期、手动补录都用 `maxAgeHours`。
  - 优先消息的时效不再比普通消息长。
- **一次性迁移**：
  - 时机：启动时，在打开服务前执行，照人设升级的做法先备份 `settings.json`。
  - 若 `migrations.messageAge` 不存在：
    1. 计算 `next = triage.normalMaxAgeHours ?? min(3, program.maxAgeHours ?? config.maxAgeHours ?? 6)`；
    2. 写入 `program.maxAgeHours = next`；
    3. 置 `migrations.messageAge = 1`；
    4. program 与 triage 的修订号各加一。
  - `triage.normalMaxAgeHours` 原值保留在文件里，新代码不读（回退用，规划时决定）。
  - 生产当前为 6 / 3，迁移后为 3。
- **接口**：
  - `GET /api/triage/settings` 增加只读字段 `maxAgeHours`。
  - `PUT /api/triage/settings` 可带 `maxAgeHours`。服务端在同一个同步读改写中合并到 program 分区：校验 1–48，program 修订号加一，返回两边的新修订号（规划时决定，页面只需一个保存按钮）。
  - `PUT /api/program/settings` 仍接受 `maxAgeHours`，兼容旧调用。
  - 两个接口收到 `normalMaxAgeHours` 时都忽略。
- **配置样例**：`config.example.json` 的 `maxAgeHours` 改为 3，并同步 `docs/` 中说明两档时效的段落。

## 5. 定时任务（`task-settings.js`）

- **时间轴**：
  - 用 SVG 或绝对定位的 div，高约 92px：
    - 轴上方两行交错放任务名，避免重叠，用细线连到轴上的点；
    - 轴下方每 3 小时一个刻度；
    - 回复关闭区间用斜线底纹，区间左端写“不回复”。
  - “现在”标签用北京时间。
  - 只画按每天固定时间执行的任务；主循环、宿主健康检查这类按间隔执行的任务不画。
  - 回复区间来自 `/api/program` 的 `replyHours`。关闭跟随后不画底纹。
- **表格**：
  - 按计划时间排序，每个任务一行：开关、名称、时间、上次执行、行内“单次执行”。
  - 计费任务的“单次执行”带“计费”标记。
  - “会发到 X”标签挂在会发帖的任务上（早安帖、晚安帖），无论是否启用。
  - 上次执行失败时，结果以告警色常显。
- **高级设置**：主循环间隔（秒，可改）、宿主健康检查间隔（秒，只读，注明“宿主维护状态只读”）。
- 时间轴与表格读取同一份编辑中的数据，修改时间后立即重排、重画；保存规则不变。

  | 运行、发送 | 日志阶段与队列 |
  | 数据库备份 | 定时任务 |
  | 其他（含证书） | 不显示入口 |

- **分组格**：宽屏三列。每组的标题行写组名和“全部正常”或“N 项需关注”，下面是指标胶囊（圆点加名称），`title` 与 `aria-label` 为“名称：状态，说明”。
- 账号组仍显示检查时间与“检查计划”。
- **日报表**：列不变，金额用 `fmtUsd`，未知值显示“—”。
- 告警历史默认收起；“健康与披露配置”放进 `advanced('health', …)`。

## 11. 日志阶段与队列（`program.js`）

- **事件摘要表**：新增 `EVENT_SUMMARY`，类型对应到“类别 + 摘要函数”。至少覆盖生产中已见的类型（规划时决定，文案可在实施时微调）：

  | 类型 | 类别 | 摘要 |
  | --- | --- | --- |
  | `model-library-refresh` | 模型 | “{服务商} 模型列表已刷新” |
  | `browser-restart` | 浏览器 | “浏览器进程重启” |
  | `persona-create` / `persona-save` / `persona-delete` | 人设 | “新建 / 保存 / 删除人设「名称」（第 N 版）” |
  | `persona-upgrade` | 人设 | “人设升级，已自动备份” |
  | `boot` | 服务 | 原文 |
  | `pause` | 控制 | 原文 |
  | `health-control` | 健康 | “健康控制：暂停 / 运行 / 人工” |
  | `takeover` / `release` | 接管 | 原文 |
  | `account-compliance` | 账号 | “账号合规检查：……”，按字段拼接缺失项 |

  实施时 grep 源码中全部事件类型补齐。未登记的类型显示类型名和原文。
- **行**：时间、类别标签（浏览器重启等告警类用告警色）、摘要、行尾浅色原始内容（截断到一行）。点击行展开完整 JSON 和关联 ID 链接。
- **日期分隔**：按北京日期，写“今天 · 10/29”“昨天 · 10/28”“10/27”。
- **筛选行**：级别、渠道、搜索（内容或关联 ID，输入停 300ms 后生效）、时间范围（最近 1 天 / 3 天 / 7 天 / 自选），右侧是回复时段状态和“暂停实时日志”。删除“筛选日志”按钮和原来分开的开始、结束输入框。时间范围默认最近 3 天（规划时决定）。
- “阶段”“队列”视图改用同样的表格样式，数据与列不变。

## 12. 任务执行历史（`task-settings.js` 的 `mountHistory`、`scheduler.ts`）

- **接口**：`GET /api/tasks/runs` 的返回增加 `counts:[{task,total,failed}]`，按当前查询的时间范围统计，不受分页影响。
- **合并**：前端实现 `groupRuns(runs)`。相邻且 `task`、`status` 都相同的成功记录并为一组，显示次数、起止时间、平均耗时、合计费用（全部无费用时显示“—”）。
  - 失败、取消、运行中的记录不合并。
  - 加载更多时，新一页的第一组与已有的最后一组如果可合并，就接上。
  - 组行点击展开，显示逐次记录；单条记录点击展开详情和关联调用（原有内容）。
- **筛选**：分段按钮“全部 N”和各任务名加次数，再加“只看失败”切换。两者都走原接口的查询参数，后端已有 `task`、`status` 过滤；若缺少，在 `history()` 中补上（规划时决定）。

## 17. 失败处理与回退

- 星标或协议保存冲突时，按现有修订号冲突提示，刷新后重试。
- 最近使用的聚合查询失败时，模型表退化为两块（星标、其他），不影响页面。
- 任务历史计数失败时，筛选按钮不显示次数。
- 回退：
  - 恢复上一版镜像即可；
  - `provider.api` 和 `triage.normalMaxAgeHours` 原值仍在文件里，旧代码可直接使用；
  - 回退后消息时效按旧代码为“处理时效 3 / 普通 3”。如需恢复 6 小时，管理员在旧页面改回；
  - 星标与 `migrations` 字段对旧代码无影响。
