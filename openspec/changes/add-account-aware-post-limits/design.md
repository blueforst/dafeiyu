# 账号发帖长度策略技术设计

## Context

动机、范围及官方资料差异见 [proposal.md](proposal.md)，行为契约见 [x-posting-limits 规格](specs/x-posting-limits/spec.md)。

现有代码有四处不同边界：`model.ts` 的结构解析和 `browser.ts`／`outbox.ts` 的正文保护各限制 4,000 个 JavaScript 字符；公开正文另用默认 `parseTweet(text).valid` 限为 280 加权字符。`Identity` 没有订阅或发帖能力字段。生产回复、问候任务与公开试聊各自调用长度校验，生成提示词没有对应账号的长度策略。

浏览器现有回执解析主要依赖响应中的 `legacy.full_text`，尚不能保证长帖完整正文。应用在浏览器 RPC 前就把出站置为 submitting，普通异常会落入 unknown；直接抛出新增长度错误会把明确未提交混成未知。现有 unknown 只回查和冻结正文要求必须保留。

未归档的七页提案在 `x-message-workflow` 的“额度退避与正文校验”中要求公开正文通过加权校验。本提案将该约束扩展为“短帖加权校验，长帖按已确认规则校验”；实施时同步旧提案的对应条款和交叉引用，保留其小时额度及平台拒绝退避。本次创建独立提案，不修改旧任务完成状态，也不提前将其能力写入主规格。

## Goals / Non-Goals

**目标：** 用同一份有版本的策略贯穿能力识别、生成、预览、持久出站与浏览器提交，区分字数限制、资源保护、模型 token 与实际平台提交结果。

**边界：** 复用当前 app／browser、SQLite 和串行控制，不接入新的平台 API 套餐或权限代理。只覆盖既有原创问候帖和公开回复；不新增发帖编辑器，不为长帖主动提高生成长度。

## Decisions

### 1. 账号能力是带来源的快照

新增 `PostingCapability`，分别保存 `post`、`reply`：`accountId`、可确认时的 `userId`、浏览器会话标识、`status`、`limit`、`countingMode`、`source`、`checkedAt`、`expiresAt`、`revision` 与失败原因。状态为 confirmed、unknown、stale；订阅档位仅作展示信息。浏览器重启、更换账号、退出登录和人工接管释放后使旧会话证据失效。

来源仅限当前页面实际取得且可绑定自身账号的原生能力数据，或能明确证明对应权限／上限的官方界面。实施先采集脱敏样本确定字段，不凭字段名猜含义，不反向构造私有接口，不为探测权限点击发送。缺失明确数字时只能在已验证的能力与版本规则有可靠映射的情况下推导；映射失效即回退。

默认缓存有效期十五分钟，用于展示与生成。超过短帖的提交必须在本次浏览器串行操作内取得仍有效的账号／能力证据，并检查实际编辑器反馈。可复用本次页面已取得的数据，不额外建立轮询器。普通短帖不因无法确认订阅而停止。

选择能力证据而非“蓝标即长帖”的映射，是因为标记、档位、操作类型及可用功能并非同一概念。暂不提供管理员强制放开权限的配置，以免配置值取代平台事实。

### 2. 共用计数策略与独立资源保护

新增纯函数模块 `src/posting-policy.ts`，输入正文、操作类型和能力快照，输出 `allowed`、`measuredLength`、`limit`、`unit`、`policyRevision`、`capabilityRevision`、`reason`。app 与 browser 使用相同策略实现，browser 自行选择其可信快照，不接受 RPC 提供的上限作为授权。

- 短帖继续使用既有 `twitter-text` 的完整有效性和加权长度，包含 Unicode、emoji 与空正文等校验。
- 长帖使用有版本、已验证的计数适配器。不得仅提高短帖配置中的 `maxWeightedTweetLength` 就声称与长帖一致；样本必须覆盖汉字、emoji、ZWJ、组合字符和边界。
- 只有资格、数字上限和适配器全部确认才启用长帖；否则为 280 加权字符。现阶段资源保护最多接收 25,000 个规范化 Unicode 码点，另验证完整序列化 RPC 不超过既有请求体限制；该资源边界不声明平台采用相同计数。若实际确认的能力更低，采用更低值。
- `parseDraft` 拆分结构／禁用内容检查与按渠道的长度检查。公开正文不再先被 4,000 个 JS 字符拦下；私信保留现有 4,000 门槛。公开正文的 NFC 规范化在生成完成、冻结正文之前统一进行，冻结后不得再次改变文本。

使用共享模块可避免生成端、存储端和浏览器分别维护不同数字。资源上限独立于平台权限，防止把移除旧门槛理解成无限输入。

### 3. 生成数据流与失败行为

生产回复：`当前身份 → reply 能力快照 → 共用提示词组装 → 模型调用 → 结构校验／规范化 → 长度校验 → 出站 → 浏览器复核`。

问候帖采用同一链路的 `post` 策略；公开试聊使用当前账号缓存快照，无法绑定账号则显式模拟普通账号，不为试聊操作真实页面。接口返回所用上限、计数单位与来源状态。私信试聊仍使用私信原规则。

最终生成提示词明确长度单位及上限，保持人格、语义触发、记忆可见范围和固定规则。长度上限是约束而不是要求写满；保持模型设置、默认 4096 token、OpenCode 稳定会话及既有计量。无额外语义请求，无自动缩写重试。

结构有效但超长时，回复保留在 `messages.draft`；问候帖使用尚未提交并已标明取消原因的出站记录保存候选正文。`outbox.prepare` 可保存资源边界内的候选，但 `begin` 必须取得有效校验结果，不能仅凭 prepared 状态进入发送。超出资源保护边界的输出只记录错误与计数，不持久化超大原文。已有模型调用按实际结果计费。

选择停止并保留草稿，而非自动截断或自动生成多帖，避免改变原意、出站数量和费用预期。

### 4. 提交边界与确定未提交结果

在 app 校验后、浏览器保存提交意图前，browser 再核对账号、操作类型、权限及最终编辑器状态。即使编辑器按钮可用，也不能单独证明长帖权限；它仅是最后的发送条件之一。所有操作沿用串行入口，提交前继续检查暂停、目标和身份。

扩展内部发送结果为原 `Receipt` 加 `not_submitted` 分支，包含有界错误码、计数、上限和策略修订。只有能确认尚未存在本次提交意图、没有进入点击路径时，才能返回该分支。browser 在独立版本化预检结果文件中先持久保存该出站标识的终态，再返回结果；该文件与原 `TransportJournal` 分开，避免让旧日志读取器误解析。

同一出站标识的未提交终态不可自动转为再次提交；后续 lookup 可返回原预检结果，解决响应丢失后 app 暂时进入 unknown 的情况。该结果文件中的未对账项不得因数量清理丢失，可在 app 确认终态后按有界保留策略清理。若写盘失败或证据不足，保持 unknown，不自称确定未提交。

app 收到或回查确认 `not_submitted` 后，将相应 outbox 置为 cancelled，回复保留草稿并标注失败，问候任务记为 skipped，实际原因可查看。cancelled 不进入 `Outbox.count`；只有真正的 rejected 继续进入既有拒绝和四小时冷却路径。收到 HTTP 异常或普通超时仍按原 unknown 收束。

已存在的提交日志、confirmed、rejected 或 unknown，必须先走原回查／终态路径，再判断新的长度策略；失效权限不能阻止历史回查。browser 已保存提交意图后即使点击失败，也不以新的预检分支规避未知状态。

此显式结果优于把长度异常塞进普通异常或 `rejected`，因为后两者分别产生无法收束的 unknown 或错误的四小时冷却。

### 5. 完整长帖回执

扩展 `PlatformTweet` 的正文完整性信息。在已观察到的网页响应中选择经过样本验证的完整长帖正文来源；保留普通 `legacy.full_text` 路径，不能仅因该字段存在就认为长帖完整。必要时通过现有串行浏览器读取对应详情页及“显示更多”，不构造私有请求。

回执仍要求唯一平台 ID、正确作者、准确回复关系、原提交时间及完整正文一致。只有截断预览或相同前缀时继续 unknown；不得用省略号删除、前缀匹配或新生成正文代替完整比对。原创与回复分别验证，避免同文其他帖子误认。

直接放宽发送长度而不适配回执，会使成功的长帖无法确认，因此完整正文解析是长帖启用的前置条件。

### 6. 状态接口、刷新与界面

拟增加以下受现有鉴权保护的接口，名称在实现时与已有路由核对：

| 接口 | 行为 |
| --- | --- |
| `GET /api/account/posting-limits` | 读取当前账号缓存、按时效计算的状态及生效策略，不导航、不调用模型 |
| `POST /api/account/posting-limits/refresh` | 显式刷新，复用工作流互斥及 browser 串行队列，不改变控制模式 |
| browser 内部 `/capabilities` | 返回浏览器自行绑定账号的能力证据摘要，不接受调用方声明权限 |

刷新在人工接管或排空时返回 409 并说明原因。暂停时仅允许读取现有页面和已观察响应；证据不足则回退，不为刷新导航或恢复 auto。运行时的安全读取复用当前串行操作。所有 GET 与 SSE 只读缓存，不能以状态订阅为由不断访问 X。

主页面账号区域显示原创／回复上限、单位、检查时间与未知原因；主程序在现有小时发送额度旁单列字数约束，避免把“10 次／小时”和“280 加权字符”混为一个额度。消息和任务详情显示长度判定；公开试聊显示当前账号或普通模拟策略。保持七页结构，外部字符串按纯文本渲染。

### 7. 持久化与兼容

能力快照按账号、类型和浏览器会话存入现有 runtime 命名空间；重启后旧记录仅供展示，重新确认前不授权长帖。新增可重复的 SQLite 迁移，为 outbox 加可空 `validation_json`，保存生成／提交时使用的策略和最后校验结果，默认 NULL 的旧记录表示未验证，不回填虚构权限。消息详情通过 source_id 关联校验结果。

新增 JSON 元数据不复制 Key、原始账号响应或额外正文。问候候选正文只存既有 outbox.text；普通日志仅记录关联 ID、类型、实际计数、上限、错误码及修订。更新迁移回退工具和备份恢复说明，迁移编号以实施时的真实注册表为准。

## Risks / Trade-offs

- 官方长帖说明不一致、平台字段和计数变化 → 使用可绑定账号的实际证据和版本化适配器；缺失就回退短帖，不将文档数字直接变成权限。
- 缓存过期或生成期间订阅失效 → 生成快照便于解释，长帖在本次提交操作内再确认；仍无法排除平台瞬时变化，真实拒绝保持原退避。
- 同一账号的编辑器可能支持原创却不支持某类回复 → 按操作类型确认，不扩大为统一布尔权限。
- 新结果分支处理不完整导致卡在 submitting → 回归正常响应、响应丢失、重启和回查对账，所有发送消费者必须穷尽处理结果。
- 长帖正文在时间线或响应中被截断 → 完整正文是确认及启用长帖适配的条件；证据不足保持 unknown，禁止重发。
- 长帖生成可能超过现有 token 额度 → 保留已有设置；说明平台上限并非输出承诺，不自动增加成本。

## Migration Plan

1. 在服务器独立 staging 使用脱敏账号能力、编辑器及完整长帖样本验证适配；普通和长帖计数未通过时不得启用对应长帖路径。不挂载生产 profile 跑模拟测试。
2. 实现共用策略和加法迁移，回归旧库重复迁移、私信、短帖、模型会话、计量及备份恢复。先让 app 与 browser 都理解 `not_submitted`，再启用动态能力。
3. 构建和自动化验收均在服务器执行。发布前排空并暂停业务、核对未收束出站、备份数据库和两类浏览器日志；成对更新 app／browser，不能让旧 app 接收新结果分支。
4. 真实验收分为只读权限证据、编辑器计数和获授权后的实际收发／唯一回执。当前账号没有长帖能力时如实登记限制，不为验收购买订阅或制造长帖发送。
5. 回退时先暂停，保留数据库、冻结正文和所有未收束记录。使用已验证的回退工具处理新增列，恢复兼容 app／browser；旧版固定短帖规则继续生效，超长 prepared 记录保持 cancelled，unknown 不重发。旧浏览器不能可靠回查新增长帖类型，因此回退前须完成长帖对账，或保留兼容的只读回查工具及新日志，不能强制清空 unknown。原提交日志格式保持兼容，新增预检文件单独保留。

## Verification

服务器隔离测试覆盖：普通短帖 ASCII／中文边界、长帖已确认上限前后、NFC／emoji／ZWJ、错误账号／类型／会话、证据冲突、缓存过期、权限降级、浏览器直连绕过、公开试聊、问候窗口、未提交终态及丢失响应、真实拒绝退避、unknown 在降权后的回查、完整正文与截断前缀区分、旧数据迁移与恢复，以及七页界面的鉴权和无隐式恢复。

测试通过只证明实现及模拟契约。平台权限、实际点击和唯一回执分别留证，未完成的真实长帖验收不得记为通过；具体步骤见 [tasks.md](tasks.md)。

## 与动态面板的并行实施

本提案的“主页面／主程序”展示职责在五页候选中对应动态首页与设置的发送限制；旧七页地址由面板精简提案映射。字数策略、来源和修订不因导航合并而改变。
