# 回复提示词结构增量规格

## Purpose

规定回复生成时提示词各部分的先后顺序、关键规则在生成位置附近的重申方式，以及不依赖模型的动态提醒，使同一天内的稳定前缀可以被服务商缓存复用，并减少迟到问候错误、语言混用和批量回复模板化。

## ADDED Requirements

### Requirement: 稳定前缀分层顺序

系统 MUST 按固定顺序组装回复提示词：system 只包含固定系统约束、已保存静态人格和按渠道固定的规则；user 依次为角色经历、当日日程与当前时段、对此人的允许范围记忆、当前对话、提醒区、本次消息，最后为当前时间。同账号、同渠道、同一人设修订、同一北京日期内，system MUST 逐字节一致。

#### Scenario: 两条消息命中不同触发规则
- **WHEN** 同一天同渠道的两条消息分别命中不同的触发规则
- **THEN** 两次请求的 system 完全相同，差异只出现在 user 的提醒区及之后

#### Scenario: 管理员保存新人设
- **WHEN** 人设修订号变化后开始下一轮生成
- **THEN** system 使用新人设，同一修订内的后续请求再次保持一致

### Requirement: 命中模块靠近生成位置

本轮命中的触发规则正文 MUST 放在 user 的提醒区，位于当前对话之后、本次消息与当前时间之前；system 不得包含只属于本轮命中的模块正文。

#### Scenario: 命中管理员配置的“不给步骤”规则
- **WHEN** 消息询问做法并命中该规则
- **THEN** 该规则正文出现在提醒区，而不在 system 中

### Requirement: 回复判断提醒

启用时系统 MUST 在每次回复生成的提醒区附带一条固定短提醒，要求先按系统规则判断是否回复；该提醒不得改写 system 中的跳过规则，也不得强制模型回复。

#### Scenario: 明显的广告消息
- **WHEN** 当前消息是明显广告且回复判断提醒已启用
- **THEN** 提示词提醒区包含该提醒，模型仍可按约定格式返回跳过

### Requirement: 北京时间与时段

提示词末尾 MUST 提供精确到分钟的北京时间、星期和时段名称；当日日程部分只提供当前时段，不包含分钟级时间。

#### Scenario: 北京时间深夜
- **WHEN** 服务器 UTC 时间为 15:30，北京时间为 23:30
- **THEN** 提示词显示北京时间 23:30 与深夜时段，不出现 UTC 时间

#### Scenario: 同一时段内多次请求
- **WHEN** 同一时段内相隔数分钟处理两条消息
- **THEN** 两次请求的日程与时段部分相同，只有末尾当前时间不同

### Requirement: 迟到提醒

当消息具有可靠平台时间且早于当前时间超过配置阈值（默认六十分钟）时，系统 MUST 在提醒区加入迟到提醒，要求自然致歉一次并按现在的时间问候；平台时间不可靠时不得加入迟到提醒。

#### Scenario: 早上的消息晚上处理
- **WHEN** 一条北京时间 08:10 的消息在 20:30 被处理且时间可靠
- **THEN** 提醒区说明对方约十二小时前发来，并要求按晚上的时间问候

#### Scenario: 时间不可靠
- **WHEN** 消息缺少可靠平台时间
- **THEN** 提示词不包含迟到提醒

### Requirement: 回复语言提醒

系统 MUST 用确定性规则判断消息的主要书写系统；消息主要为繁体中文、日文、韩文或拉丁字母语言时，提醒区要求用对方的语言回复，繁体中文消息要求不混用简体字形。消息为简体中文或无法判断时不加入该提醒。

#### Scenario: 繁体中文消息
- **WHEN** 消息包含足够数量的繁体特有字形
- **THEN** 提醒区要求以繁体中文回复且不混入简体字形

#### Scenario: 只有表情和标点
- **WHEN** 消息只包含 emoji、颜文字或标点
- **THEN** 不加入语言提醒

### Requirement: 开头去重提醒

系统 MUST 从同账号最近若干条角色已生成回复中提取开头片段（默认最近十二条），在提醒区要求本条不用相同的开头和句式。公开回复只参考公开回复；私信回复只参考公开回复和同一会话的私信回复，不得引用其他私信会话的内容。

#### Scenario: 最近回复多次以同一短语开头
- **WHEN** 最近十二条公开回复中有多条以同一叠词开头
- **THEN** 提醒区列出这些开头并要求本条避免使用

#### Scenario: 其他私信会话的回复
- **WHEN** 系统为某私信会话生成开头去重提醒
- **THEN** 列出的开头不包含其他私信会话中的回复片段

### Requirement: 表情节制提醒

系统 MUST 统计同渠道最近回复中颜文字、emoji 与“～”的使用，按配置决定本条允许使用的类型：上一条已使用颜文字时本条不允许颜文字；任一类型在最近十条中达到配置上限时本条不允许该类型。

#### Scenario: 上一条用了颜文字
- **WHEN** 同渠道上一条回复包含颜文字
- **THEN** 提醒区说明本条不要使用颜文字

#### Scenario: “～”达到上限
- **WHEN** 最近十条回复中已有一条使用“～”且上限为一条
- **THEN** 提醒区说明本条不要使用“～”

### Requirement: 动态提醒不增加模型请求

动态提醒 MUST 只由本地数据和确定性规则产生，不得为此发起模型请求或产生计费记录；每类提醒都可以在人设页单独关闭，关闭后从下一轮起不再加入。

#### Scenario: 关闭全部动态提醒
- **WHEN** 管理员关闭全部动态提醒并保存
- **THEN** 下一轮提示词仍按分层顺序组装但没有提醒区内容，模型调用次数与关闭前相同

#### Scenario: 生成中修改提醒设置
- **WHEN** 管理员在一轮生成进行中保存新的提醒设置
- **THEN** 当前生成继续使用原设置，下一轮使用新设置

### Requirement: 提醒可见与记录

试聊与生产 MUST 使用同一组装逻辑；试聊预览按实际请求顺序展示分段，并列出本轮加入的动态提醒及原因；生产消息详情记录提醒类别并关联该次调用的缓存读取 token。常规日志不得包含提醒中的回复片段或消息正文。

#### Scenario: 查看一次试聊
- **WHEN** 管理员完成一轮试聊
- **THEN** 页面按实际请求顺序显示 system 与 user 各分段，并列出实际加入的迟到、语言、开头或表情提醒

#### Scenario: 查看常规日志
- **WHEN** 一条回复加入了开头去重提醒
- **THEN** 常规日志只记录提醒类别，不包含列出的开头片段
