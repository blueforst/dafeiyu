# 回复提示词结构与动态提醒提案

## Why

当前回复提示词把固定约束、静态人格、本轮命中的触发模块和当日日程一起放进 system，当前时间以 UTC ISO 毫秒写在 user 末尾。触发命中每条消息都可能不同，导致 system 前缀随消息变化、服务商前缀缓存难以复用；深夜按 UTC 判断时段容易问候错误；“不给步骤”这类远离生成位置的规则约束力弱；批量回复也没有开头去重和表情频率控制，容易模板化。参考帖子验证过的几类代码层提醒（迟到致歉、回复语言、换个说法、表情节制、末尾重申要不要回）在本项目中都还没有，需要在七页提案的人设与语义触发之上补齐，并且不增加模型请求。

## What Changes

- 固定提示词分层顺序：system 只放固定系统约束、已保存静态人格和按渠道固定的规则；user 依次为角色经历、当日日程与当前时段、对此人的记忆、当前对话、提醒区（本轮命中模块与动态提醒）、本次消息，最后是精确到分钟的北京时间。同账号、同渠道、同一人设修订、同一北京日期内 system 逐字节一致。
- 本轮命中的触发模块正文从 system 移到 user 末尾提醒区，靠近生成位置；提醒区默认附带一条短提醒，要求先按系统规则判断要不要回。
- 新增不调用模型的确定性动态提醒：
  - 迟到提醒：消息可靠平台时间早于当前一小时以上时，提示自然致歉一次并按现在的时间问候。
  - 回复语言：消息主要不是简体中文时，提示用对方语言回复；繁体中文消息不混入简体字形。
  - 换个说法：列出同渠道最近十几条回复的开头，要求本条不用相同开头和句式。
  - 表情节制：根据同渠道最近回复对颜文字、emoji 与“～”的使用情况，决定本条允许使用哪些。
- 当前时间改为北京时间（含星期和时段名称），日程部分只提供当前时段，避免分钟级变化破坏前缀。
- 人设页可单独开关每类动态提醒并调整阈值，保存后下一轮生效；试聊与生产使用同一组装逻辑，试聊预览按实际请求顺序展示分段并列出本轮加入的提醒及原因。
- 生产消息详情记录本次加入的提醒类别，并可关联该次调用的缓存读取 token，便于排查与后续回放对比。

## Capabilities

### New Capabilities

- `reply-prompt-context`：回复提示词的分层顺序、生成位置附近的规则重申、确定性动态提醒及其可见性。

### Modified Capabilities

无。现有主规格中的模型配置、导航与记忆要求不变。本能力补充未归档 `add-seven-page-production-bot` 的 `persona-management`：语义触发判定、规则命中、人格生效和试聊隔离语义保持不变，本提案只规定命中正文与动态提醒在提示词中的位置。实施时同步该提案中“提示词与命中结果预览”的分段说明，不提前写入主规格。

## Impact

- 影响 `src/persona.ts`（分层顺序、提醒区、分段元数据）、`src/workflow.ts`（传入消息可靠时间与最近回复摘要）、`src/store.ts` 或新增的回复风格模块（按渠道读取最近回复开头与表情使用）、人设页试聊预览和消息详情接口。
- 面板设置新增动态提醒段（各提醒开关与阈值），沿用现有修订号和“下一轮生效”语义；不新增数据库表，消息详情元数据为可空增量字段。
- 不新增模型请求，不改变模型配置、OpenCode 会话路由、默认 4096 token 回复上限和 CommandCode 未定价语义，不改变语义触发的判定方式与计费。
- 缓存是否命中取决于服务商与 Pi 适配器；本提案只保证前缀稳定并展示实际返回的缓存读取 token，不承诺具体命中率。
- 与 `add-persona-replay` 共用回复风格检测（开头、表情）；与 `add-account-aware-post-limits` 的长度策略提示同属按渠道固定规则，放在 system。
- 本次只创建规划文件；构建、测试在服务器隔离环境执行，不改变线上运行状态。
