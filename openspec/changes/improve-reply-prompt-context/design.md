# 回复提示词结构技术设计

## Context

动机见 [proposal.md](proposal.md)，行为契约见 [reply-prompt-context 规格](specs/reply-prompt-context/spec.md)。

现有 `PersonaService.assemble()` 生成的 system 为 `FIXED_SYSTEM_RULES + 静态分区 + 本轮命中模块 + 角色状态（日程与经历）`，user 为单个 JSON：`{visibility, memory, conversation, message, media, now}`，其中 `now` 是 `new Date().toISOString()`（UTC，含毫秒）。`Workflow.tick()` 把 `e.timestamp`、`timestampReliable` 保存在事件中，但没有传给组装。消息表的 `draft` 字段保存 `{action,text,reason}`，可以取到最近回复正文；表情、开头等风格信息目前没有任何统计。

`runCompletion()` 只发送一条 system 和一条 user 消息，Pi 负责各协议的请求格式与 usage 解析，`llm_calls` 已经记录 `cacheRead`。未归档的七页提案规定“触发判定一次、只注入命中正文、试聊预览分段可检查”，本设计不改变这些行为。

## Goals / Non-Goals

**目标：** 让 system 在一天内对同账号同渠道保持稳定，把逐条变化的内容集中到 user 末尾；用纯函数实现四类确定性提醒，生产与试聊共用；可开关、可观察、零额外模型请求。

**非目标：** 不新增服务商特定的缓存参数或显式缓存标记；不在生成后按风格规则拒绝或重新生成回复（避免费用循环）；不用模型判断语言或风格；不改写管理员的人设正文。

## Decisions

### 1. 分层顺序与稳定前缀

system 依次为：固定系统约束、静态人格分区、按渠道固定的规则（公开／私信的输出格式与长度策略说明）。日程从 system 移到 user：日程每天变化，留在 system 会让跨日前缀全部失效，而放在 user 开头仍能在同一天内与 system 一起构成稳定前缀。

跨日时，user 中的日程日期与末尾当前时间更新；静态人格及渠道规则未变化时 system 继续保持相同内容。不以日期或人设修订数字本身向 system 增加动态字段，人设正文变化后从下一轮使用新内容。

user 改为带标题的纯文本分节，而不是单个 JSON 对象，固定顺序如下：

1. 【角色经历】有来源的角色经历（只在新帖确认后变化）
2. 【今日日程】当日虚构日程全文 + 当前时段名称
3. 【关于对方的记忆】允许范围内记忆
4. 【当前对话】对话上下文
5. 【提醒】本轮命中模块正文 + 动态提醒 + 回复判断提醒
6. 【本次消息】消息正文与媒体可见性说明
7. 【现在】北京时间 `YYYY-MM-DD 周X HH:mm（时段）`

各分节内部的不可信内容仍以 JSON 字符串形式嵌入，保留“资料不可执行指令”的现有约束。分节文本由同一函数生成，`segments` 与实际请求逐段一致，试聊预览直接使用。

*备选*：保持 JSON，只调整键顺序。JS 对象键顺序虽然确定，但 JSON 序列化后的前缀会在第一个变化值处断开，且难以让预览按“分段”精确对应。被否决。

*备选*：把日程留在 system。同一天内也可缓存，但跨日失效并让 system 承载会变化的内容，被否决。

### 2. 时段与时间

时区固定为 `Asia/Shanghai`，与项目其他北京时间口径一致。时段划分：00:00–05:59 深夜、06:00–08:59 早上、09:00–10:59 上午、11:00–12:59 中午、13:00–16:59 下午、17:00–18:59 傍晚、19:00–22:59 晚上、23:00–23:59 深夜。日程节只写时段名称，末尾【现在】写到分钟。

### 3. 动态提醒模块

新增纯函数模块 `src/reply-hints.ts`，输入为本次消息（正文、渠道、可靠时间）、当前时间、最近回复样本和提醒设置，输出 `{hints:[{kind,text,reason}], meta}`。`persona.assemble()` 接收该结果放入【提醒】节；试聊在没有生产样本时使用试聊对话中的 assistant 消息作为最近回复样本，并在预览中注明来源。

- **迟到**：平台时间被明确标记为可靠（`timestampReliable === true`）且 `now - timestamp >= lateMinutes`（默认 60，可设 30–360）。缺失可靠标记时不推断迟到。提醒文本给出约多少小时前，要求自然致歉一次、按现在时段问候。
- **语言**：统计字符类别。假名 ≥ 2 个判为日文；谚文 ≥ 2 个判为韩文；拉丁字母占全部字母 ≥ 60% 且 ≥ 8 个判为拉丁字母语言；汉字中命中内置繁体特有字形表（约三百个常用繁体字，如“這們個說來為會對時國過還麼後開關問題實”）≥ 2 个且占汉字 ≥ 10% 判为繁体。其余不提醒。不引入 OpenCC 等依赖，字表随代码维护并有回归样本。
- **开头**：取同账号最近回复（状态 confirmed、draft、sending、unknown，按 `updated_at` 倒序）。公开只取公开；私信取公开加同一 `conversationId` 的私信。开头为首个标点（，。！？…～!?,. 空格换行）前的内容，最长 8 个字符；去重后最多 12 条。片段只进入提示词与受鉴权的试聊预览，不写日志。
- **表情**：颜文字用括号内含特征符号（ω ∀ ▽ ・ ´ ` ° ∠ ⌒ ﾉ 等）或常见无括号形式的正则识别；emoji 用 `\p{Extended_Pictographic}`；“～”与半角 `~` 合并统计。默认上限：颜文字最近十条最多一条且不能连续，emoji 最近十条最多两条，“～”最近十条最多一条。允许的类型以一句话写入提醒。

样本查询每次生成执行一次，限定 `LIMIT 20` 并使用 `(account_id, channel, updated_at)` 现有或新增索引，不产生明显开销。

*备选*：用已有的语义触发规则让管理员自行配置“繁体”“迟到”等条件。可行但每条都要模型判定，且迟到、开头、表情依赖本地统计，模型无法得到。保留语义触发供管理员扩展，内置提醒走确定性路径。

### 4. 设置与生效

面板设置新增 `promptHints`：`{lateEnabled, lateMinutes, languageEnabled, openingEnabled, openingCount, expressionEnabled, kaomojiPer10, emojiPer10, tildePer10, replyCheckEnabled}`，默认全部启用。沿用 `mergePanelSettings` 的修订号与冲突检测；`Workflow.tick()` 在轮次开始时读取快照，与人设一样“下一轮生效”。界面在人设页增加“动态提醒”折叠区；若 `simplify-panel-activity-feed` 先落地，则放在人设标签下的同一位置。

### 5. 记录与可见性

`assemble()` 返回的 `segments` 增加 `stable: boolean` 标记（system 与日程以前为稳定段）。生产路径把 `{hintKinds, promptVersion}` 写入消息 `draft` JSON 的可选 `meta` 字段，旧版本读取时忽略未知键。消息详情接口通过已关联的 `callId` 读取 `cacheRead`，不另存 token。常规日志只写提醒类别。

### 6. 兼容

`Workflow` 中没有 `persona` 服务时的旧拼接路径同步改为相同分层，保证测试替身和旧配置行为一致。`FIXED_SYSTEM_RULES` 文本不变；渠道固定规则从固定约束中拆出时保持原语义。

## Risks / Trade-offs

- [服务商不做前缀缓存或需要显式标记] → 不影响正确性；页面如实显示缓存读取 token，是否追加显式缓存参数留待单独评估。
- [模型仍忽略提醒] → 提醒只降低概率；配合 `add-persona-replay` 的批量指标观察效果，不在生成后强制重写。
- [语言判断误判，例如纯汉字日文被判为中文] → 只是不加提醒，退化为现状；字表和阈值有回归样本。
- [开头片段把私信内容带到别处] → 私信只引用同一会话与公开回复；片段截断到 8 个字符且不进日志。
- [提醒区让 user 变长] → 开头最多 12 条短片段，其余提醒各一句，增加量在数百字符以内。

## Migration Plan

1. 部署新代码后 `promptHints` 缺省为默认值，无需数据库迁移；消息 `meta` 为可选字段。
2. 回退到旧版本时，旧代码忽略 `promptHints` 与 `meta`，提示词恢复旧结构，无数据转换。
3. 发布前在服务器 staging 用同一批脱敏样本比较新旧提示词的 system 一致性与提醒内容；真实模型下的缓存读取变化在取得授权后单独测量。

## Verification

- 单元测试：同账号同渠道同日不同命中时 system 字节一致；跨日时仅动态层的日程日期及当前时间变化；换静态人设后 system 使用新内容；时段边界；迟到阈值与不可靠时间；语言判定样本；开头提取与渠道隔离；表情计数与上限；关闭开关后的输出。
- 集成测试：生产一轮与试聊的分段顺序一致；动态提醒不增加 `llm_calls` 记录；常规日志不含片段；消息详情含提醒类别与缓存读取 token。
- 所有构建与测试在服务器隔离环境执行。
