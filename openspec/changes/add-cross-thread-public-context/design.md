## Context

现有记忆策略默认最近三条、七天窗口，可配置条数 1–30、天数 1–365。主规格要求近期入站可作为上下文，只有 confirmed 回复能视为已经说过的话；`improve-reply-style` 已将其放入独立的“与对方的近期往来”，要求避免重复用语。公开线程合并仍以同一 conversationId 为边界。

本轮管理员要求不同帖子下同一个人也注入相关上下文。代码检查发现，现有近期路径主要读取已处理状态，其他线程仍排队或处理中而尚未完成的可靠入站可能缺失；提示词也需要标注来源，避免把另一帖子误解为当前线程的父消息。跨帖历史召回与精确旧 unknown 封存是独立行为，本 change 不承担后者实现。

## Goals / Non-Goals

**Goals:**

- 在同账号、同公开用户、public 范围内召回允许窗口内的可靠跨帖入站及已确认回复。
- 排除当前消息并明确每项来源，把其他帖子只作为同人相关背景。
- 保持当前帖子平台目标、队列和合并独立；沿用配置上限、遗忘和输出确认语义。
- 保存实际生成上下文证据，确认真实不同帖子样本确实进入了模型输入。

**Non-Goals:**

- 不将不同用户、工作账号或私信原文合并进当前公开会话，不创建隐式身份映射。
- 不按内容相似度猜用户或线程，不用模型筛选历史，不改变 system 稳定前缀。
- 不改变私信召回、公开 source 资格、采集周期、队列优先级、线程合并、outbox 或发送门禁。

## Decisions

### 可选当前事件引用

`MemoryService.context(userId, channel, accountId, at, policyOverride, currentEvent?)` 增加可选当前公开事件引用，字段为 id／platformId／conversationId。工作流传入实际正在生成的 event；试聊复用该组装入口并传入其事件。原有管理预览及旧调用继续兼容。

仅 public 且当前 conversationId 是可靠数字线程标识时采用有来源的公开召回；其他调用保留原路径，不将缺失当前线程身份视为可靠跨帖关系。查询和注入发生在生成前，不发起额外模型或平台请求。

### 同人公开候选及有界筛选

候选严格按 accountId、userId 和 public 渠道筛选，在策略时间窗口内按平台时间倒序读取，扫描上限 `max(30, recentCount * 5)`，最终返回最多 recentCount 条并按时间正序呈现。维持默认三条／七天及既有字段范围，不扩大生成输出上限或长期摘要预算。

已处理状态仍可提供入站。其他线程还允许 queued／approved／generating／sending／unknown／merged 的可靠来言，补齐尚未轮到回复的同人背景；当前线程这些未处理消息由平台上下文和合并消息负责，不重复注入。以本地 ID 或平台 ID 排除本次消息，只有 confirmed 且非空的 draft.text 附带角色已发回复。

每项必须具有一致的账号、userId、public 渠道、作者 handle、非空正文、数字平台 ID 和 conversationId；可靠平台时间须与已保存 created_at 一致并处于过去的允许窗口。公开链接必须为对应作者及平台 ID 的规范 `https://x.com/.../status/...`，不得有用户凭据、查询或锚点。平台列冲突、关系冲突、不可靠线程标记、未来时间和格式异常均跳过，不用当前时间或其他用户替补伪造证据。

选择已有确定性字段筛选而非放宽所有同名记录，是为了将跨帖召回限定在已取得的可靠生产入站。扫描有界，异常项过多时可能返回少于条数上限；不会扩大为无限历史读取。

### 提示词及快照

每项 recent 附带 platformId、conversationId、url、timestamp、status 和 `same-public-thread`／`other-public-thread` 关系。user 的“与对方的近期往来”保留在记忆之后、当前对话之前，明确原文是谁说的、哪些回复已确认，以及其他帖子只是同人公开背景，不能当作当前线程上文或本条正在回答的目标。

system 固定前缀及现有重复用语提醒保持。生成快照保存本轮实际 context，真实验收检查该快照或实际请求，不以离线预览代替本次模型输入。日志只记录关联元数据，不复制往来正文。

### 隐私、遗忘及原有行为

遗忘用户在 context 入口直接返回空；恢复后的记录继续遵循既有独立遗忘与恢复账本，不复活旧资料。跨帖查询只读 public；管理员显式关联允许的私信长期背景、八字重合草稿保护和原私信上下文路径保持既有规则，不因跨帖扩大身份或渠道范围。

历史条目不会被重新排队、合并、消费或发送，recall 对消息状态没有写入副作用。不同帖子的队列和 outbox 目标仍各自校验，即使两条消息来自同一人也不能误用另一帖子 ID。

## Risks / Trade-offs

- 同一人在不同帖讨论无关主题 → 标明其他帖背景及来源，不伪装为当前祖先；模型按本次消息和目标作答。
- 扩大到未处理入站可能误称角色已回复 → 只有 confirmed 附带 reply，草稿、unknown 和 approved 均只提供来言。
- 历史身份或关系字段不一致 → 严格跳过冲突项；缺少可靠证据时宁可少召回，不按相似内容推断。
- 候选扫描有界可能遗漏更早可用项 → 沿用有限近期策略并覆盖异常候选测试，不为召回历史扫描全部消息。
- 输入更完整可能增加本次请求 token → 不新增模型请求，沿用当前条数与文本边界，按实际统一流水计费。

## Migration Plan

1. 服务器隔离验证同／跨线程、排队与确认、当前消息排除、账号／用户／渠道隔离、窗口、遗忘及提示词来源说明，运行适用完整回归与构建。
2. 发布时保留模型、profile、数据库 schema14、旧出站和控制；与精确 unknown 封存共同发布时分别保留来源散列及回退说明。
3. 用已授权同一对端在两个不同帖子制造真实来言，核对两条实际平台线程和目标；第二条生成快照包含第一帖可靠往来且标明其他帖，发送回执仍指向第二条原目标。
4. 分别记录模型输入、费用、平台唯一回执和本轮公开清理。回退恢复旧代码即可恢复原召回，不反向迁移、不删除记忆或消息、不重发已确认内容。

## Open Questions

召回范围与独立线程边界已明确。真实来源字段、模型实际输入及自然衔接效果仍由实际样本验收，不能用代码存在或模拟 fixture 提前判定通过；若真实页面缺少可靠线程标识，应保留缺失事实并继续修复适配，不能改成跨人召回。
