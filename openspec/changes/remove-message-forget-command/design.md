# 取消消息里的遗忘指令技术设计

## Context

动机见 [proposal.md](proposal.md)，行为契约见 [conversation-memory 规格](specs/conversation-memory/spec.md)。以下现状来自 2026-10-28 本机提交 `b607c3d` 和生产服务器只读核对：

- **入队阶段**：`Workflow` 主循环在 `queue` 阶段逐条处理采集到的事件。正文 `trim()` 后匹配 `/^忘(了|记)?我吧[。！!\s]*$/` 时调用 `store.forget(userId, handle)` 并 `continue`；匹配 `/^重新记住我[。！!\s]*$/` 时调用 `store.remember(userId, handle)` 并 `continue`。两种情况都不进入分级，也不入库。
- **已遗忘用户**：`store.ingest` 遇到已遗忘用户直接返回 `false`，消息不入库、不回复。这个行为保留。
- **记忆页**：`POST /api/memory/users/:id/forget` 和 `/remember` 已支持管理员遗忘和恢复，遗忘写入独立账本 `forget-ledger.json`，恢复旧数据库后仍生效。
- **固定系统约束**：`FIXED_SYSTEM_RULES` 已有“不作做不到的承诺”，但没有针对删除记录的说法。上一次加句（看不到主页等）时版本从 `reply-context-v1` 升到 `reply-context-v2`。
- **生产**：`/var/lib/role-workflow/app/` 下没有 `forget-ledger.json`，即从未有人被遗忘。
- **修改前基线**：回归用例已在服务器隔离目录 `/srv/role-workflow-forget-cmd-20261028` 对 `b607c3d` 运行，按预期失败（“忘了我吧”的用户被遗忘）。

## Goals / Non-Goals

**Goals：**

- 消息内容不改变遗忘状态。
- 用户要求删除记录时，回复不声称已经删除。

**Non-Goals：**

- 不新增“识别删除请求并通知管理员”的机制。管理员通过动态页和记忆页自行处理。
- 不改变已遗忘用户的消息处理（仍不入库、不回复）。
- 不改记忆页、遗忘账本和恢复流程。

## Decisions

### 1. 直接删除两条判断

`src/workflow.ts` 入队阶段的两行删除后，这类消息走普通的分级与入库流程。不保留开关，也不改成“只提醒管理员”，因为误触比真实需求常见，而真实需求已有记忆页可以处理。

### 2. 固定系统约束加一句

在“不作做不到的承诺。”之后加入：

> 被要求忘掉对方、删除聊天记录或记忆时，不说已经忘了或删了；如实说明自己做不到，记录由运营者管理。

`REPLY_PROMPT_VERSION` 改为 `reply-context-v3`，让回放和快照能区分新旧约束。放在固定约束而不是人设分区，是因为这条对任何人设都成立，管理员没有理由删掉它。

### 3. 不处理历史数据

生产从未有人被遗忘，不需要迁移。今后若有管理员遗忘的用户，只能由管理员在记忆页恢复。

## Risks / Trade-offs

- **真心要求删除的人要等管理员处理**：回复只会说明做不到、由运营者管理，删除要等管理员在动态页看到后去记忆页操作。可以接受：这类请求很少，管理员每天都会看动态页和日报。
- **模型仍可能说“我忘了”**：固定约束能降低但不能杜绝。真实模型验收时用固定试题检查（见 Verification）。

## Migration / Rollback

无数据迁移。回退时恢复两行判断和旧固定约束、版本号改回 `reply-context-v2` 即可；期间产生的数据不受影响。

## Verification

- **服务器单元测试**：
  - 未遗忘用户发“忘了我吧”：消息入库、生成回复，用户不被遗忘。
  - 已遗忘用户发“重新记住我”：用户仍保持遗忘，消息不入库。
  - `FIXED_SYSTEM_RULES` 包含新句，`REPLY_PROMPT_VERSION` 为 `reply-context-v3`。
  - 服务器类型检查与全量回归通过。
- **真实模型抽查**（计费调用，需要另行授权；可并入 `add-persona-presets` 的批量验收）：“忘了我吧”“把我们的聊天记录删掉”两条试题，回复不声称已经忘记或删除。
- **生产发布**（需要另行授权）：随下一次发布上线，发布记录写明消息指令已取消。
