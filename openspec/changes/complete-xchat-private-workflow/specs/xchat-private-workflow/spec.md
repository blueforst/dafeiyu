## Purpose

为服务器角色工作流补齐 X 新 Chat 的正常一对一新用户私信处理，使请求发现、规则过滤、接受、可靠读取、回复及回执核对形成可观察且可恢复的闭环，并在归属、时间或提交结果不可靠时保留明确状态，避免漏收与重复回复。

## ADDED Requirements

### Requirement: 分别核对私信来源

系统 MUST 分别检查平台实际提供的普通收件箱、请求及隐藏来源，并报告已检查、空、未检查、失败与截止；普通来源为空不得代表全部私信为空。扫描 MUST 有界并按会话去重。

#### Scenario: 主收件箱为空但存在请求
- **WHEN** 主收件箱为空而平台提供请求入口
- **THEN** 系统继续检查请求来源，列出请求候选或准确的检查失败原因

### Requirement: 可靠原生消息事件

系统 MUST 仅将账号、会话、发送者、稳定原生 ID、完整正文及可靠时间相互绑定的入站消息放入队列，保留原生证据版本；不完整、冲突、自发、群聊或旧观察字段 MUST 不被猜测为有效入站。

#### Scenario: 显示时间缺少机器证据
- **WHEN** 页面仅提供 Today 和分钟标签且无已验证精度方案
- **THEN** 系统报告时间未确认，不以采集时间或 UUID 推出发送时间

### Requirement: 按规则接受正常请求

系统 MUST 在自动运行且回复时段、私信额度、冷却和 unknown 状态允许时，复用现有广告过滤、骚扰冷却及遗忘保护，自动接受归属明确且可可靠读取的正常一对一请求。广告、骚扰、已遗忘、群聊及不明确请求 MUST 保留并记录原因，不删除或屏蔽。接受之后 MUST 重新读取事件并进入原有分级、记忆和回复流程。

#### Scenario: 正常新用户请求
- **WHEN** 请求证据完整、现有规则通过且当前允许自动处理
- **THEN** 系统核对唯一原生接受控件，接受后重新确认会话并入队

#### Scenario: 自动条件不允许
- **WHEN** 系统暂停、人工接管、草稿模式、关闭时段或达到私信额度
- **THEN** 系统可以观察请求但不自动接受或提交回复

### Requirement: 接受及发送结果持久恢复

系统 MUST 在点击接受或提交回复前保存原始意图及所需平台证据；持久化失败不得执行动作。结果未知或重启后 MUST 仅按原意图回查，不通过同文猜测成功或重新执行。回复确认 MUST 具备本次意图绑定的平台确认，含糊、冲突或缺原意图继续 unknown。

#### Scenario: 接受后超时重启
- **WHEN** 接受动作已记录但结果尚未确认时进程重启
- **THEN** 系统核对会话实际状态，不能再次点击或错误标记已接受

#### Scenario: 同文出站冲突
- **WHEN** 有多个同文候选或无法证明消息属于本次提交
- **THEN** 系统保留 unknown 并只回查，不能发送第二条

### Requirement: 状态可诊断且兼容回退

系统 MUST 在现有采集、动态及健康接口准确区分未检查、规则保留、待人工、接受未知、已入队和发送待回查，普通日志不得包含私信正文或认证信息。旧公开与私信出站保护 MUST 保留，回退不得丢失意图或重发未知消息。

#### Scenario: 回退旧版本
- **WHEN** 新版本存在未知接受或发送记录并回退到既有版本
- **THEN** 意图仍被保留，旧版本不将其作为未提交动作自动重发
