# 正常流程试聊规格

## Purpose

让管理员以测试用户的身份，在公开或私信里和角色连续对话，消息按生产的正常流程处理：分级、合并、冷却、记忆召回与整理、日程、人设与触发卡、提醒、模型生成和校验都与真实用户相同。回复不发到 X，不占额度，不受时段限制；测试用户的数据单独存放，不进入生产。

## ADDED Requirements

### Requirement: 测试用户

管理员 MUST 能新建、改名、重置、清除冷却和删除测试用户，最多五十个。每个测试用户有显示名（一至三十字）和测试用 handle（一至十五位小写字母、数字或下划线，库内唯一，新建时自动生成，可修改）。与生产中的同一个 X 用户一样，测试用户在公开和私信中是两个身份：公开按 handle 识别，私信按一个固定的测试私信会话识别；记忆、近期往来、冷却和整理进度按身份分开。重置 MUST 清除该测试用户两个身份的全部消息、记忆、冷却和整理进度，但保留用户本身；删除 MUST 一并移除其全部测试数据。左栏 MUST 按最近活动时间排列测试用户，并显示相对时间。

#### Scenario: 新建测试用户
- **WHEN** 管理员点击新建并填写显示名“小林”
- **THEN** 左栏顶部出现“小林”，有一个自动生成的测试 handle，没有任何消息和记忆

#### Scenario: 重置测试用户
- **WHEN** 管理员重置一个已有十轮对话和两条长期记忆的测试用户
- **THEN** 该用户的对话、长期记忆、近期往来、冷却和整理进度全部清空，显示名和 handle 不变

### Requirement: 按正常流程处理

每条试聊消息 MUST 按生产中相同渠道的真实消息处理，使用与生产相同的规则和代码：分级（广告与刷量过滤、首次来访、提问、老面孔招呼等）、同一用户连发合并、骚扰冷却、记忆召回（长期记忆、近期往来、角色经历）、当天虚构日程的当前时段、人设分区与触发卡（关键词卡与语义卡）、提示词提醒、使用中的模型和参数、模型跳过判断、公开或私信的字数校验与格式标记。公开和私信的记忆 MUST 与生产一样按身份分开：私信这一轮只召回私信身份的记忆，公开只召回公开身份的记忆。被过滤的消息 MUST NOT 调用模型。

#### Scenario: 记得上一轮
- **WHEN** 测试用户先说“项目下周上线”，角色回复后，再问“还记得我在忙什么吗”
- **THEN** 第二轮的近期往来包含第一轮的消息和回复，本轮详情列出这条召回

#### Scenario: 广告被过滤
- **WHEN** 测试用户发送带链接的广告关键词消息
- **THEN** 本轮显示被分级过滤及原因，没有模型调用和费用

#### Scenario: 公开与私信记忆分开
- **WHEN** 测试用户在公开回复中提到养猫并已整理成长期记忆，之后在私信里问“你记得我养了什么吗”
- **THEN** 私信这一轮不召回公开身份的“养猫”记忆，与生产中同一个人的公开和私信身份不互通一致；右栏记忆标签分别显示两个身份的记忆

#### Scenario: 关键词卡命中
- **WHEN** 使用中的人设带“被夸”关键词卡，测试用户说“你好可爱”
- **THEN** 本轮命中“被夸”，详情显示命中的关键词，且只有一次回复生成请求

### Requirement: 额度与时段豁免

试聊 MUST NOT 检查或占用任何发送额度，包括每小时公开与私信额度、每轮条数、公开每日额度及后续新增的私信每日额度；MUST NOT 受排队时效、回复时段、运行状态（暂停、运行、排空）、浏览器人工接管、自动或草稿模式、未收束出站和平台拒绝退避的限制。试聊 MUST NOT 访问浏览器，也 MUST NOT 改变运行状态。

#### Scenario: 暂停且额度已满时试聊
- **WHEN** 业务处于暂停状态，当前小时公开额度已用完，管理员发送一条公开试聊消息
- **THEN** 消息被立即处理并得到回复；业务仍暂停，额度计数不变

#### Scenario: 人工接管期间试聊
- **WHEN** 浏览器处于人工接管中
- **THEN** 试聊照常可用，没有浏览器请求，接管状态不变

#### Scenario: 隔天继续聊
- **WHEN** 测试用户的上一条消息是二十小时前发送且尚未处理，管理员点击让角色回复
- **THEN** 该消息照常处理，不因超过排队时效被跳过

### Requirement: 视为已发出与记忆整理

模型给出、且通过字数校验的回复 MUST 视为已向该测试用户发出：计入近期往来和同人去重样本，与生产中已确认的回复相同。未通过字数校验的回复 MUST 显示“正常流程不会发出”及原因，不算已发出。模型选择跳过时 MUST 显示跳过原因，并按生产规则记录冷却。每个测试用户的已处理消息 MUST 按生产阈值触发记忆整理；管理员也可以手动立即整理。整理结果只写入测试数据。

#### Scenario: 回复超长
- **WHEN** 公开回复超过当前账号允许的加权字符数
- **THEN** 本轮显示回复正文和“正常流程不会发出：超出字数”，下一轮近期往来不包含这条回复

#### Scenario: 第五条触发整理
- **WHEN** 测试用户的第五条消息处理完成
- **THEN** 对话中出现一条记忆整理结果提示，右栏记忆标签显示新增的长期记忆和费用

#### Scenario: 骚扰达到冷却条件
- **WHEN** 模型在一天内第三次以骚扰为由对测试用户的私信选择跳过
- **THEN** 本轮显示跳过原因和私信冷却结束时间（二十四小时后）；冷却期间该用户的新私信显示“骚扰冷却”且不调用模型，公开消息不受影响，直到管理员清除冷却或冷却结束

### Requirement: 先攒几条再回

输入框 MUST 提供“先攒几条再回”开关。开启时发送的消息只入队、不处理；管理员点击“让角色回复”后，系统 MUST 按生产的采集与分级规则一起处理已入队的消息：私信只把最后一条作为本轮消息，之前攒下的几条作为同一会话的上文，与生产采集私信时只取最后一条入站消息相同；公开消息按生产分级的同人合并规则，把三十分钟内排队的多条合并为一轮。对话中 MUST 标明哪些消息作为上文或被合并。关闭时每条消息发送后立即处理。

#### Scenario: 两条私信一起处理
- **WHEN** 开关开启时测试用户连发“在吗”和“在吗在吗？？”两条私信，然后管理员点击让角色回复
- **THEN** 只有“在吗在吗？？”作为本轮消息，“在吗”作为上文出现在提示词中；本轮只有一次回复生成

#### Scenario: 两条公开消息合并
- **WHEN** 开关开启时测试用户在十分钟内发了两条公开消息，然后管理员点击让角色回复
- **THEN** 两条按生产的同人合并规则合并为一轮，较早的一条标为已合并

### Requirement: 选择人设

每条试聊消息 MUST 使用发送时选定的一个已保存人设处理，默认是使用中的人设；可选范围只包括“我的人设”中已保存的版本，不包括编辑器里未保存的修改和内置预设。处理开始时 MUST 固定该人设当时的内容与修订号，处理中保存或切换人设不影响这一轮。同一测试用户可以先后用不同人设聊天，记忆和冷却属于测试用户，不随人设改变。

#### Scenario: 用未使用的人设试聊
- **WHEN** 管理员在人设模式点击“大肥鱼 · 温柔版”的“试聊这个人设”
- **THEN** 页面切换到试聊，输入框选中该人设；回复使用其已保存版本，生产的使用中人设不变

#### Scenario: 有未保存修改时试聊
- **WHEN** 管理员改了一个人设但未保存，就去试聊这个人设
- **THEN** 页面提示试聊只使用已保存版本，回复不包含未保存的修改

### Requirement: 隔离存储与只读生产来源

测试用户的消息、回复、记忆、冷却、整理进度和本轮诊断 MUST 存放在与生产业务数据库分开的独立数据目录中，拥有独立的遗忘与删除账本。这些数据 MUST NOT 出现在动态页、记忆页、额度与队列统计、健康检查、日报、回放样本、质量统计、生产近期往来或业务数据库备份中。试聊 MUST 只读取生产中属于账号层面的内容：人设库、模型与参数、提示词提醒、分级设置、当前账号当天的虚构日程（不触发生成）、已确认的角色经历、账号字数能力和账号近期公开回复（用于同人以外的去重）；MUST NOT 修改它们。当前账号未确认时，依赖账号的内容按空处理，并在页面提示。

#### Scenario: 试聊后生产数据不变
- **WHEN** 管理员进行二十轮试聊并触发两次记忆整理
- **THEN** 生产数据库的消息、记忆、冷却和出站记录数量及内容均不变；动态页和记忆页没有测试用户

#### Scenario: 当天没有日程
- **WHEN** 当前账号当天没有虚构日程
- **THEN** 试聊按生产规则使用“暂无当日日程”，不触发日程生成，也不产生日程费用

#### Scenario: 账号未确认
- **WHEN** 浏览器当前账号未确认时进行试聊
- **THEN** 试聊照常进行，字数按普通账号规则校验，页面提示日程、角色经历和账号近期回复为空

### Requirement: 本轮诊断

每一轮 MUST 在对话中显示一行摘要（所用人设、分级结果、召回条数、命中的卡片、耗时），回复下方显示模型、输入和输出 token 以及费用。点击某一轮后，右栏“本轮详情” MUST 显示：人设名称与修订号、分级档位与原因、合并条数、日程时段、触发卡命中及原因、提示词提醒、模型与调用次数、耗时、字数校验和格式标记、本轮实际召回的记忆；“提示词”标签 MUST 按实际请求顺序显示各提示词分段及其属于稳定前缀还是动态内容。“记忆”标签 MUST 分公开身份和私信身份显示该测试用户当前的长期记忆、近期往来、距下次整理的进度和骚扰计数，以及只读的角色经历。任何展示都 MUST NOT 包含密钥。

#### Scenario: 查看某一轮的提示词
- **WHEN** 管理员点击第三轮回复并切换到提示词标签
- **THEN** 右栏按顺序显示该轮的系统层和消息层分段，包括当时召回的记忆和日程，不含任何 Key

### Requirement: 试聊计量

试聊产生的每次实际模型请求，包括回复生成、语义触发判定和记忆整理，MUST 写入统一调用流水，用途记为“试聊”，并能区分是哪一步；计费页 MUST 把“试聊”作为单独用途统计。主区页头 MUST 显示当前测试用户的累计估算费用。生成失败、输出不合格或中止后已经落账的用量 MUST 仍计入；没有可靠价格时显示未定价或未知，不视为免费。

#### Scenario: 计费页按用途查看
- **WHEN** 管理员进行了若干轮试聊后在计费页按用途查看
- **THEN** “试聊”单独成为一个用途，其请求数和费用与试聊页显示的累计一致

### Requirement: 失败、取消与并发

同一测试用户同一时间 MUST 只处理一轮，处理期间输入框显示进行状态并禁止再次触发处理；整个面板同时进行的试聊处理 MUST 不超过两轮，超出时提示稍后再试。管理员 MUST 能取消正在进行的一轮；取消或失败的一轮 MUST 显示原因，消息回到待处理状态，不算已发出，可以重试；重试会再次计费。人设在处理开始前已被删除时，这一轮 MUST 被拒绝并提示重新选择人设。

#### Scenario: 模型请求失败后重试
- **WHEN** 一轮因模型服务错误失败，管理员点击重试
- **THEN** 同一条消息重新处理；失败那次已落账的用量和重试的用量都出现在调用流水中

#### Scenario: 第三个并发试聊
- **WHEN** 已有两个测试用户正在处理，管理员让第三个测试用户回复
- **THEN** 第三个请求被拒绝并提示稍后再试，前两个不受影响
